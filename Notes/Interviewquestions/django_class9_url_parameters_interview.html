Django URL Parameters

Views • URL configurations • dynamic routes • path() • re_path() • kwargs

Click Show Answer after trying each question yourself.

1. Core concepts you must know

Views with parameters

A view can receive values captured from a URL.

def user(request, user_id):
    return HttpResponse(user_id)

URL configuration

A URLconf maps URL patterns to view callables. Django checks patterns in order and uses the first matching pattern.

path("user/<int:user_id>/",
     views.user)

Project main URLs

The root URLconf can delegate a URL prefix to an app using include().

path("blog/",
     include("blog.urls"))
Interview sentence: Django URL routing maps an incoming path to a view, captures dynamic values from the route, and passes named captured values to the view as keyword arguments.

3. Interview questions — fundamentals

1What is URL routing in Django?

Answer

URL routing is the process of matching an incoming URL path with a URL pattern and then sending the request to the matching view. Django normally checks urlpatterns from top to bottom and stops at the first match.

Interview tip: Say “URLconf maps URL patterns to views.”

2What is a dynamic URL? Why do we need it?

Answer

A dynamic URL contains a value that can change for each request. For example, /blog/1/ and /blog/2/ can use one route with <int:id> instead of separate routes for every blog.

3Explain <int:user_id> in path().

Answer

int is the path converter and user_id is the variable name. Django matches an integer and passes the converted value to the view as user_id.

path("user/<int:user_id>/", views.user)

# /user/25/
# view receives user_id=25

4What is the difference between path() and re_path()?

Answer

path() uses readable path converters such as int, str, slug, and uuid. re_path() uses regular expressions. Use path() for most normal routes and re_path() when regex matching is actually needed.

5When would you choose re_path()?

Answer

Choose re_path() when the URL rule cannot be expressed cleanly with Django's path converters and a regular expression gives the required matching rule.

re_path(
    r"^article/(?P<year>[0-9]{4})/$",
    views.article
)

6What is kwargs in a Django view?

Answer

kwargs is a Python dictionary used to collect named keyword arguments. A view can use **kwargs to receive multiple named URL values without declaring every name separately.

def product(request, **kwargs):
    # kwargs might be:
    # {"productid": 101, "productname": "Laptop"}
    ...

7Is kwargs a URL-routing method like path()?

Answer

No. path() and re_path() define URL patterns. **kwargs is a Python function parameter that collects named keyword arguments passed to the view.

8What happens if the URL variable name and view parameter name do not match?

Answer

For a normal named route parameter, Django passes the captured value using that route name. If the view does not accept that keyword, the call can fail with an unexpected keyword argument error.

# Route
path("user/<int:user_id>/", views.user)

# Wrong view
def user(request, id):
    ...

# Correct
def user(request, user_id):
    ...

9Why is URL pattern order important?

Answer

Django checks URL patterns in order and stops at the first match. Therefore, a broad pattern placed before a more specific pattern can capture a URL before the intended pattern gets a chance.

10What does include() do in project urls.py?

Answer

include() delegates URL matching to another URLconf, commonly an app's urls.py. This keeps project-level routing and app-level routing organized.

path("blog/", include("blog.urls"))

11How does a class-based view connect to path()?

Answer

Pass the result of as_view() to path().

from .views import UserDetailView

path(
    "user/<int:user_id>/",
    UserDetailView.as_view(),
    name="user-detail"
)

12Does Django's URLconf inspect GET or POST parameters when matching a route?

Answer

No. URLconf matching is based on the requested URL path. Query-string data such as ?page=3 is not part of the URL pattern matching process.

4. Code-based interview questions

13Write a route for /product/101/ and pass the ID to the view.

# Write your answer here first.
Expected answer
# urls.py
path("product/<int:product_id>/",
     views.product,
     name="product")

# views.py
def product(request, product_id):
    return HttpResponse(
        f"Product ID: {product_id}"
    )

14What is wrong with this code?

# urls.py
path("user/<int:user_id>/", views.user)

# views.py
def user(request, id):
    return HttpResponse(id)
Expected answer

The URL captures a keyword named user_id, but the view expects id. Rename the view parameter or route variable so they agree.

def user(request, user_id):
    return HttpResponse(user_id)

15Write a route for username + user ID using path().

# Requirement:
# /user/Sai/25/
# username = "Sai"
# user_id = 25
Expected answer
path(
    "user/<str:username>/<int:user_id>/",
    views.user
)

def user(request, username, user_id):
    return HttpResponse(
        f"{username} - {user_id}"
    )

16Convert this regex route to a path() route.

re_path(
    r"^article/(?P<year>[0-9]{4})/$",
    views.article
)
Expected answer
path(
    "article/<int:year>/",
    views.article
)

This is simpler when the requirement is simply “a positive integer year.”

17Use re_path() to accept exactly a four-digit year.

# Requirement:
# /article/2026/
# exactly four digits
Expected answer
re_path(
    r"^article/(?P<year>[0-9]{4})/$",
    views.article,
    name="article"
)

With re_path(), captured regex values are passed as strings. If you need an integer, convert it in your application logic or use a suitable path() converter where exact four-digit validation is not required.

18Use **kwargs to handle two dynamic URL values.

# URL:
# /product/101/Laptop/
Expected answer
# urls.py
path(
    "product/<int:product_id>/<str:product_name>/",
    views.product
)

# views.py
def product(request, **kwargs):
    product_id = kwargs["product_id"]
    product_name = kwargs["product_name"]

    return HttpResponse(
        f"{product_id} - {product_name}"
    )

19Find the output for this route.

path(
    "user/<int:id>/<str:name>/",
    views.user
)

def user(request, id, name):
    return HttpResponse(
        f"{id}:{name}"
    )

# Request:
# /user/10/Alex/
Answer

The output is 10:Alex. Django converts 10 to an integer because of the int converter.

20What is wrong with this route?

path("/user/<int:id>/", views.user)
Expected answer

Django URL patterns normally should not begin with a leading slash. Use:

path("user/<int:id>/", views.user)

21Write the project URL configuration for an app called users.

# project/urls.py
# Connect the users app under /users/
Expected answer
from django.urls import path, include

urlpatterns = [
    path(
        "users/",
        include("users.urls")
    ),
]
5. Scenario-based interview questions

22You have 10,000 products. Would you create 10,000 URL patterns?

Strong answer

No. I would create one dynamic route such as products/<int:product_id>/. The product ID changes per request, while the same view can fetch and display the requested product.

23A route works for /user/25/ but not /user/abc/. Why?

Strong answer

If the route uses <int:user_id>, Django expects an integer. abc does not match that converter. If text is required, use <str:user_id> or another suitable converter.

24Your application has hundreds of URLs. How would you keep urls.py maintainable?

Strong answer

Keep app-specific routes in each app's urls.py, use include() from the project URLconf, give routes meaningful names, and avoid unnecessary regex when path() is enough.

25A regex route and a normal path route both match a URL. Which one runs?

Strong answer

The first matching URL pattern in urlpatterns runs. This is why URL order matters.

6. Common interview traps
Trap 1: Saying kwargs creates the URL. It does not. It collects keyword arguments in Python.
Trap 2: Saying re_path() is always better. Regex is more flexible but usually less readable.
Trap 3: Forgetting that <int:id> converts the value to an integer.
Trap 4: Using MyView instead of MyView.as_view() for a class-based view in path().
Trap 5: Putting a broad route before a more specific route and then wondering why the specific route never runs.
Trap 6: Confusing URL path parameters with query parameters such as ?page=2.
