CLASS-60: DRF with GenericAPIView & Mixins

Concepts, full project code & your doubt on queryset / serializer_class naming

1. What is GenericAPIView?

generics.GenericAPIView is a base class DRF provides that adds the common plumbing every API view needs — but none of the actual logic (list, create, retrieve, etc).

It gives you ready-made helper methods and attributes:

  • self.get_queryset() → returns self.queryset
  • self.get_serializer_class() → returns self.serializer_class
  • self.get_object() → fetches a single object using the URL pk
  • self.get_serializer(...) → builds a serializer instance correctly
  • Pagination, filtering, permission hooks already wired in
Think of GenericAPIView as the "engine" — it knows how to fetch data and build serializers, but it does not know what to do on GET, POST, PUT, DELETE. That's where Mixins come in.
2. What are Mixins?

Mixins are small, reusable classes that each implement one CRUD action as a ready-made method. They rely on GenericAPIView's helpers (get_queryset, get_serializer, etc.) to actually do the work.

MixinMethod it addsMaps to
ListModelMixin.list()GET (all)
CreateModelMixin.create()POST
RetrieveModelMixin.retrieve()GET (one)
UpdateModelMixin.update()PUT / PATCH
DestroyModelMixin.destroy()DELETE
A Mixin alone is useless — it has no get_queryset() or get_serializer() of its own. It borrows those from GenericAPIView.
3. Why use GenericAPIView + Mixins together?

They're two halves of one system:

GenericAPIView
queryset + serializer_class + helper methods
Mixins
.list() .create() .retrieve() .update() .destroy()

Working API view
You just call the mixin method inside get()/post()/etc.

Without GenericAPIView, the Mixins have no data source. Without Mixins, GenericAPIView has no CRUD behaviour. Combining them = reusable, DRY class-based views instead of writing raw queryset/serializer logic in every method by hand (like plain APIView forces you to).

4. When should you use this combo?
  • You want standard CRUD behaviour but need to customize one or two things (e.g. override get_queryset() to filter by logged-in user, or add extra logic before saving).
  • You want more control than generics.ListCreateAPIView (the fully pre-built shortcut) but don't want to write everything from scratch like plain APIView.
  • You're learning DRF internals — this pattern shows exactly what the shortcut generic views (ListCreateAPIView, RetrieveUpdateDestroyAPIView) do under the hood.
Rule of thumb: plain APIView → too much boilerplate. Generic + Mixins → full control, still DRY. ListCreateAPIView/RetrieveUpdateDestroyAPIView → fastest, least control.

6. Your doubt — must the names be queryset and serializer_class?
Yes — those two names are fixed/mandatory. You must use exactly queryset and exactly serializer_class as the attribute names. They are not arbitrary variable names you choose — they are the specific attribute names that GenericAPIView looks for internally.

Why? Because GenericAPIView's built-in methods read them by that exact name:

# (simplified — actual DRF source)
class GenericAPIView(APIView):
    queryset = None
    serializer_class = None

    def get_queryset(self):
        return self.queryset          # <-- looks specifically for "queryset"

    def get_serializer_class(self):
        return self.serializer_class  # <-- looks specifically for "serializer_class"

So if you renamed them, e.g.:

student_qs = StudentModel.objects.all()      # WRONG name
student_serializer_cls = StudentSerializer   # WRONG name

get_queryset() and get_serializer_class() would still look for self.queryset / self.serializer_class, find None, and your mixin's .list() / .create() etc. would crash with an AssertionError.

Escape hatch: if you truly want custom logic/names, don't rename the attribute — instead override the method: 
def get_queryset(self):
    my_custom_data = StudentModel.objects.filter(age__gte=18)
    return my_custom_data

def get_serializer_class(self):
    return StudentSerializer
Here the internal variable name (my_custom_data) can be anything — because you're returning it yourself, not relying on DRF to find it by attribute name.
Interview Tips
Q: Difference between APIView, GenericAPIView, and generics.ListCreateAPIView?

APIView = fully manual. GenericAPIView + Mixins = reusable helpers + you wire up HTTP methods. ListCreateAPIView = GenericAPIView + Mixins already wired for you.

Q: Can queryset/serializer_class be dynamic?

Yes — override get_queryset() / get_serializer_class() instead of setting the static attribute, e.g. to filter by request.user.

Q: What happens if you forget serializer_class?

AssertionError: "...should either include a serializer_class attribute, or override get_serializer_class()".

Q: Why use Mixins instead of writing list/create manually?

DRY — avoids repeating serializer validation, save, and Response-building boilerplate in every view.
