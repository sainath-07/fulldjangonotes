Django Session Storage

How Django remembers user-related temporary data across multiple HTTP requests.

1. What is Django Session Storage?

Definition: Django session storage is a mechanism for maintaining user-specific session data across multiple HTTP requests.

Layman meaning: HTTP requests are normally independent. A session gives the application a way to remember useful temporary information about a user's session.
Layman example

Imagine a shopping mall giving you a temporary token at the entrance. The mall can use that token during your visit to associate information with your visit. Django uses a session identifier similarly to associate requests with session data.

2. Why are Sessions Used?

Sessions help applications maintain user-specific state across requests.

Common uses
  • Shopping-cart information.
  • Temporary multi-step form data.
  • Login-related session state.
  • Temporary user preferences.
  • Short-lived workflow information.
  • Passing small pieces of state between requests.
Important:

Sessions are not a replacement for your main database. Keep session data small and appropriate for temporary state.

Example: If a user adds a phone and laptop to a cart, the application can associate cart information with that user's session so it can be available on later requests.

3. How do Django Sessions Work?

Django uses a session identifier to associate a browser with session data. The exact storage location depends on the configured session backend.

Key distinction: With Django's default database-backed session engine, the session data is stored server-side in the database while the browser carries the session key in a cookie. Django also supports other session backends.
Request → Session → View → Response
  1. Browser sends a request.
  2. Django identifies the relevant session.
  3. Your view reads, adds, changes, or deletes values using request.session.
  4. Django returns a response and persists session changes when needed.

blog/views.py
from django.shortcuts import render
from django.http import HttpResponse


def set_session(request):
    request.session['username'] = 'mohit'
    request.session['course'] = 'django full course'
    return HttpResponse('session data saved successfully')


def get_session(request):
    username = request.session.get('username', 'Guest')
    course = request.session.get('course', 'not enrolled')
    return HttpResponse(
        f'Username: {username}, Course: {course}'
    )


def delete_session(request):
    try:
        del request.session['username']
        del request.session['course']
        request.session.flush()
    except KeyError:
        pass
    return HttpResponse('Session data deleted successfully...')
Note: If your intention is to clear the entire current session, request.session.flush() is enough. The example first deletes individual keys and then flushes the session, which is redundant.

8. Common Developer Mistakes

1. Storing too much data
Sessions are not a replacement for a database.
2. Storing secrets carelessly
Do not put passwords or unnecessary sensitive data into sessions.
3. Confusing cookies and sessions
The browser may carry the session key in a cookie, while session data can be stored server-side depending on the backend.
4. Using the wrong deletion method
Use del request.session['key'] for one key; use flush() to clear the current session.

9. Interview-Ready Explanation

How to explain it:

“Django sessions provide a way to maintain user-specific state across multiple HTTP requests. Django associates a session identifier with the browser and uses it to access the corresponding session data. In the default database-backed configuration, session data is stored server-side while the session key is stored in a cookie. We can use request.session to set, get, modify and delete session values. Common examples include shopping carts, temporary form data and login-related state.”
