What is ModelViewSet?
ModelViewSet is a DRF class that combines the logic of ListModelMixin, CreateModelMixin, RetrieveModelMixin, UpdateModelMixin and DestroyModelMixin into a single class — giving you full CRUD with almost no code.

Instead of writing separate views for list, create, retrieve, update, and delete, you just define:

  • queryset — which records to work with
  • serializer_class — how to convert model ↔ JSON

All CRUD endpoints (GET list, GET detail, POST, PUT/PATCH, DELETE) are generated automatically.

What is a Router?
A Router automatically generates the URL patterns for a ViewSet, so you don't have to manually write a path() for every action (list, detail, create, update, delete).

DRF provides two built-in routers:

  • SimpleRouter — generates standard CRUD routes only
  • DefaultRouter — same as SimpleRouter, plus an auto-generated API root view (a browsable landing page listing all registered routes)

Usage pattern: router.register('students', StudentViewSet, basename='student') then path('', include(router.urls)).

GenericAPIView + Mixins vs ModelViewSet
Aspect GenericAPIView + Mixins ModelViewSet
Class structure You manually combine GenericAPIView with mixins like ListModelMixin, CreateModelMixin, etc. Everything (list, create, retrieve, update, destroy) already combined into one class.
Number of view classes Usually 2 classes needed — one for List/Create, one for Retrieve/Update/Destroy. Only 1 class handles all operations.
URLs You write each path() manually in urls.py. URLs are auto-generated using a Router (SimpleRouter/DefaultRouter).
HTTP method mapping You explicitly define get(), post() etc. calling mixin methods. Handled internally — router maps HTTP verb + URL to the right action.
Flexibility / control High — pick exactly which mixins/operations you want to expose. Lower by default, but customizable using @action decorator for extra endpoints.
Code amount More boilerplate. Minimal — fastest way to build a full CRUD API.
Best used when You need partial CRUD (e.g., only List + Create) or custom behavior per operation. You need standard, full CRUD for a model quickly.
Quick rule of thumb: If you need every CRUD operation with no special logic → use ModelViewSet + Router. If you need only some operations, or custom logic per method → use GenericAPIView + specific mixins.

Auto-Generated URLs from Router

When you call router.register('students', StudentViewSet, basename='student'), the DefaultRouter auto-generates the following URLs and maps them to ModelViewSet actions:

URL HTTP Method ViewSet Action Purpose
/students/GETlist()Get all students
/students/POSTcreate()Add a new student
/students/{id}/GETretrieve()Get one student
/students/{id}/PUTupdate()Full update of a student
/students/{id}/PATCHpartial_update()Partial update of a student
/students/{id}/DELETEdestroy()Delete a student
basename='student' is used to build internal URL names like student-list and student-detail — required especially when the ViewSet has no queryset attribute set directly, but good practice to always include.
Interview Tips
Q1. What is the difference between APIView, GenericAPIView, and ModelViewSet?

APIView = plain, you write all logic yourself. GenericAPIView = adds queryset/serializer + generic behavior, combined with mixins for CRUD. ModelViewSet = GenericAPIView + all mixins bundled + designed to be used with a Router.

Q2. Why do we need a Router if we can write path() manually?

A Router saves boilerplate — one register() call generates all list/detail URL patterns and names automatically, keeping urls.py clean and consistent, especially useful as the number of ViewSets grows.

Q3. What's the purpose of basename in router.register()?

It's used to generate the internal URL pattern names (e.g. student-list, student-detail). Django can usually infer it from the queryset, but it's required if the ViewSet doesn't define a queryset attribute.

Q4. When would you NOT use ModelViewSet?

When you need fine-grained control — e.g., only allow List + Retrieve (read-only API), or need custom logic on just one operation. In that case, GenericAPIView + specific mixins (or ReadOnlyModelViewSet) is a better fit.

Q5. Difference between SimpleRouter and DefaultRouter?

DefaultRouter adds an automatic, browsable API root view listing all registered routes, and supports .json format suffixes. SimpleRouter generates only the standard CRUD routes without the root view.

Summary
ModelViewSet
Combines all CRUD mixins into one class. Use with a Router for zero manual URL writing.
Router
Auto-generates URL patterns for a registered ViewSet (SimpleRouter / DefaultRouter).
GenericAPIView + Mixins
More manual, more control — good for partial or custom CRUD behavior.
Fastest full CRUD API
ModelViewSet + DefaultRouter is the quickest way to expose a model as a REST API.
