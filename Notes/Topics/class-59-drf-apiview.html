CLASS-59: DRF with APIView

Function-based vs API view, when to use which, and the complete project code

1. Function Based View vs APIView (Class Based)
Function Based View (FBV)APIView (Class Based)
Written as a plain Python function, usually decorated with @api_view(['GET','POST']) Written as a class extending rest_framework.views.APIView
One function handles all allowed methods with if request.method == 'POST': branching Each HTTP method gets its own dedicated method: get(), post(), put(), delete()
Simple, explicit, easy to read for small/one-off endpoints Cleaner separation of logic, easier to extend, supports inheritance and mixins
Harder to reuse logic across endpoints Reusable via inheritance — basis for GenericAPIView/Mixins/Generic views later
No built-in method routing — you write the if/elif yourself Django/DRF automatically routes GET → get(), POST → post(), etc.
Both ultimately do the same job — parse request, talk to serializer, return Response. The difference is purely about organization and scalability, not capability.
2. When to use which?
Use FBV when:
  • Endpoint is simple/one-off (e.g. a single custom action)
  • Quick prototyping or a small script-style API
  • No plan to reuse logic across multiple endpoints
Use APIView (class based) when:
  • Endpoint needs multiple HTTP methods (GET/POST/PUT/DELETE) on the same URL
  • You want to organize CRUD logic cleanly per-method
  • You're heading toward GenericAPIView + Mixins or fully generic views later
  • You need to override behaviour like permissions/auth per class
Rule of thumb: standard CRUD resource → class based (APIView or Generic views). One-off custom logic endpoint → FBV is fine.

DRF's as_view() looks at request.method and calls the class method with the same name — no manual if/elif needed.

blog_app/views.py 
from django.shortcuts import render
from rest_framework.response import Response
from rest_framework.views import APIView
from rest_framework import status
from .models import StudentModel
from .serializers import StudentSerializer

# Create your views here
class StudentApi(APIView):
    def get(self,request,pk=None):
        if pk:
            try:
                Student = StudentModel.objects.get(id=pk)
                serializer = StudentSerializer(Student)
                return Response(serializer.data,status=status.HTTP_200_OK)
            except StudentModel.DoesNotExist: 
                return Response({'error':"student not found"},status=status.HTTP_404_NOT_FOUND)
        else:
            Student = StudentModel.objects.all()
            serializer = StudentSerializer(Student,many=True)
            return Response(serializer.data, status=status.HTTP_200_OK)


#create post
    def post(self,request):
        seralizer = StudentSerializer(data= request.data)
        if seralizer.is_valid():
            seralizer.save()
            return Response(seralizer.data,status=status.HTTP_201_CREATED)

        return Response(seralizer.errors,status= status.HTTP_400_BAD_REQUEST)


# update method
    def put(self,request,pk):
        try:
            student=StudentModel.objects.get(id=pk)
        except StudentModel.DoesNotExist :
            return Response({"error":"student not found"},status=status.HTTP_404_NOT_FOUND)

        serializer = StudentSerializer(student,data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data,status=status.HTTP_200_OK)
        return Response(serializer.errors,status=status.HTTP_400_BAD_REQUEST)


# delete method
    def delete(self,request,pk):
        try:
            student = StudentModel.objects.get(id=pk)
            student.delete()
            return Response(status=status.HTTP_200_OK)
        except StudentModel.DoesNotExist:
            return Response({"error": "Student not found"}, status= status.HTTP_400_BAD_REQUEST)

from .views import StudentApi
from django.urls import path

urlpatterns=[
    path('students/',StudentApi.as_view()), # only for GET and POST api.
    path('students/<int:pk>/',StudentApi.as_view()) # for GET(single),PUT,PATCH,DELETE

Your urls.py correctly maps two paths to the same class:

  • /students/ → no pk → hits GET (all) and POST
  • /students/<int:pk>/ → pk passed in → hits GET (one), PUT, DELETE
This is the correct standard pattern for a single-resource APIView handling full CRUD, and your delete() already correctly catches StudentModel.DoesNotExist.
Interview Tips
Q: How does DRF know to call get() for a GET request in APIView?

as_view() dispatches based on request.method, matching it to a same-named method on the class (Django's View.dispatch() pattern).

Q: Why prefer APIView over plain Django View?

APIView gives you request.data (parsed), DRF's Response/content negotiation, authentication, permissions, and throttling out of the box.

Q: Can one URL map to two different methods on the same class?

Yes — as shown here, /students/ and /students/<pk>/ both point to StudentApi.as_view(); the method + presence of pk decides the branch.

Q: What's the next step up from APIView?

GenericAPIView + Mixins (less boilerplate), then fully pre-built generic views like ListCreateAPIView.

Q: Why catch StudentModel.DoesNotExist and not just Exception?

Catching the specific exception avoids silently swallowing unrelated bugs (e.g. serializer or DB connection errors) and lets you return an accurate 404.

Q: What does PATCH do differently from PUT?

PUT expects the full object (full replace); PATCH allows partial updates — needs serializer(..., partial=True) if you add it.
