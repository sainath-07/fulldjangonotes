Django Cookies

A simple, interview-ready guide to cookies, sessions, storage, security, and Django implementation.

1. What Are Cookies?

Definition

A cookie is a small piece of data that a website asks the browser to store. The browser can send that cookie back to the same website with later requests.

In simple words: A cookie helps a website remember small pieces of information between requests.
Layman example

Imagine a shop gives you a small identification card. When you visit the shop again, you show the card and the shop can recognize you. A browser cookie works in a similar way.

Important: Cookies are stored on the client side, so the user can inspect them. Do not store passwords or other sensitive secrets directly in an ordinary cookie.
2. Where Are Cookies and Sessions Stored?

🍪 Cookies

Stored: Client side, mainly in the browser.

The browser manages the cookie and sends eligible cookies with requests to the related website.

Remember: Cookie → Browser / Client

🗄️ Django Session

Session data: Stored according to Django's configured session backend. With the common database-backed session engine, the session data is stored in the database.

The browser normally stores a session ID in a cookie.

Remember: Session data → Server-side storage; Session ID → Browser
Interview clarification: Saying “sessions are stored on the server” is a useful basic explanation. Technically, Django supports different session backends, so the exact storage location depends on configuration.

4. Are Sessions More Secure Than Cookies?

The answer depends on the implementation. A server-backed session can keep sensitive application state on the server, while the browser mainly holds a session identifier. However, the session identifier itself is sensitive and must be protected.

🍪 Cookie security concerns
  • The browser can inspect cookie values.
  • Without HttpOnly, JavaScript can normally access the cookie.
  • Without Secure, a cookie can be sent over HTTP.
  • Incorrect SameSite settings can increase cross-site request risks.
🛡️ Session security
  • The actual server-side session state need not be exposed to the browser.
  • The browser normally stores a session identifier.
  • The session ID must be protected from theft and fixation.
  • HTTPS and secure cookie settings are important for authentication sessions.
Interview-ready answer: For sensitive server-managed state, a server-backed session can reduce exposure of the actual state because the browser mainly stores an identifier. But sessions are not automatically secure; the session ID and the complete authentication flow must also be protected.
5. Why Do We Use Cookies?
👤 Preferences

Remember language, theme, or other small preferences.

🛒 Shopping State

Maintain small client-side state such as a cart identifier.

🔐 Login Sessions

Browsers commonly store a session identifier in a cookie.

📊 Analytics

Websites may use cookies to recognize returning browsers, subject to applicable privacy requirements.

⚙️ Application State

Store small pieces of non-sensitive state that the browser needs to send back.

⏳ Expiring Data

Use expiration settings when information should remain only for a limited period.

7. Which One Should I Use?
Choose a cookie when...
  • The data is small.
  • The browser needs the data on future requests.
  • The information is suitable for client-side storage.
  • You are storing a preference such as theme or language.
Choose a session when...
  • The server should control the state.
  • You need login/session state.
  • You do not want the actual state exposed to the browser.
  • The state is better managed centrally by the server.
Practical rule: Keep sensitive application state server-side when appropriate. Keep cookies small and avoid putting sensitive secrets directly into them.
8. Django Example — Set, Get and Delete Cookies
Project URL configuration — innerproject/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('blog.urls'))
]
Views — blog_app/views.py
from django.shortcuts import render
from django.http import HttpResponse

# Create your views here.

def set_cookies(request):
    response = HttpResponse('Cookie set successfully')

    # max_age is in seconds
    response.set_cookie(
        'username',
        'sainath biradar',
        max_age=60 * 60 * 24
    )

    response.set_cookie(
        'course',
        'django full course',
        max_age=60 * 60 * 24
    )

    return response


# get cookies
def get_cookies(request):
    username = request.COOKIES.get('username', 'Guest')
    course = request.COOKIES.get(
        'course',
        'No Course Selected'
    )

    if 'username' in request.COOKIES:
        return HttpResponse(
            f'username: {username}, course: {course}'
        )
    else:
        return HttpResponse('No cookies found')


# delete cookies
def delete_cookies(request):
    response = HttpResponse(
        'cookie deleted successfully'
    )

    response.delete_cookie('username')
    response.delete_cookie('course')

    return response
URLs — blog_app/urls.py
from . import views
from django.urls import path

urlpatterns = [
    path(
        'set_cookies/',
        views.set_cookies,
        name='set_cookies'
    ),
    path(
        'get_cookies/',
        views.get_cookies,
        name='get_cookies'
    ),
    path(
        'delete_cookies/',
        views.delete_cookies,
        name='delete_cookies'
    ),
]
Project structure note: Your example uses include('blog.urls') but names the app folder blog_app. Ensure your real Django URL module is actually called blog.urls, or change the include path to match your project.
9. Understanding set_cookie() Options

Django provides several options when calling response.set_cookie().

OptionMeaningExample / Use
keyName of the cookie.'username'
valueValue stored in the cookie.'sainath'
max_ageMaximum lifetime in seconds.60*60*24 = 1 day
expiresSpecific expiration date/time.Useful for an exact expiry.
pathURL path for which the cookie is sent.'/' for the whole site
domainDomain for which the cookie is valid.Use carefully with subdomains.
secureCookie is sent only over HTTPS.True for HTTPS deployments
httponlyBlocks normal JavaScript access through document.cookie.Useful for cookies that JS does not need
samesiteControls cross-site sending behavior.'Lax', 'Strict', or 'None'
# Example of stronger settings for a sensitive cookie
response.set_cookie(
    'session_token',
    token,
    max_age=60 * 60,
    secure=True,
    httponly=True,
    samesite='Lax'
)
Note: The exact cookie settings should match your application's requirements. For sensitive authentication cookies, HTTPS and appropriate Secure, HttpOnly, and SameSite settings are important.

11. Common Developer Mistakes
1. Storing passwords in cookies
Never store plain passwords or private keys in cookies.
2. Forgetting HTTPS
For sensitive cookies, use HTTPS and the Secure attribute as appropriate.
3. Making sensitive cookies readable by JavaScript
If JavaScript does not need access, use HttpOnly=True.
4. Confusing cookie data with a session ID
A server-backed session usually keeps application state outside the browser while the browser stores an identifier.
5. Using a cookie for large data
Cookies are intended for small pieces of data and are sent with requests, so unnecessarily large cookies can hurt performance.
6. Assuming cookies are automatically secure
Cookie security depends on configuration and application design. Use suitable attributes and protect the overall authentication flow.
12. Interview Questions & Ready Answers
Q1. What is a cookie?
A cookie is a small piece of data stored by the browser for a website. The browser can send it with later requests.
Q2. Where are cookies stored?
Cookies are stored on the client side, inside the browser.
Q3. Where is a Django session stored?
Django session data is stored according to the configured session backend. With the common database-backed backend, the data is stored in the database, while the browser normally stores a session ID.
Q4. How does a cookie work?
The server sends a Set-Cookie response header. The browser stores the cookie. On later matching requests, the browser sends the cookie back to the server.
Q5. Cookie or session — which is more secure?
A server-backed session can keep sensitive state away from the browser, but the session ID must be protected. Neither option is automatically secure without correct configuration.
Q6. How do you set a cookie in Django?
Use response.set_cookie(key, value, ...).
Q7. How do you read a cookie?
Use request.COOKIES.get('cookie_name').
Q8. How do you delete a cookie?
Use response.delete_cookie('cookie_name').
Q9. What is max_age?
It defines the cookie lifetime in seconds.
Q10. What are Secure, HttpOnly and SameSite?
Secure restricts sending to HTTPS. HttpOnly prevents normal JavaScript access. SameSite controls when cookies are sent in cross-site requests.
