Django Signals

A simple, practical and interview-ready guide to pre_save and post_save signals.

1. What are Signals in Django?

Definition: Django Signals allow one part of a Django application to be notified when a particular event happens somewhere else in the application.

Simple meaning: A signal is like an automatic notification: “Something happened. If you are interested, you can react to it.”
Layman example

Imagine a shop. When a customer completes a purchase, the cashier system can automatically notify another system to send a receipt. The cashier does not need to manually call every other system.

In Django, the event could be “a BlogModel was saved”, and a signal handler can automatically run after that event.

2. Why are Signals Used?

Signals are useful when an action should happen automatically after or before a Django event.

Common uses
  • Send an email after user registration.
  • Create a related profile automatically.
  • Update another model after a change.
  • Create an audit/log record.
  • Perform cleanup when an object is deleted.
  • Run small side effects around model events.
Important design point

Signals can reduce direct coupling between the code that causes an event and the code that reacts to it. However, too many hidden signal side effects can make an application harder to understand and debug.

3. How do Signals Work?

Django provides many built-in signals. A receiver function listens for a particular signal. When Django sends that signal, the receiver function runs.

1. Event
Model save/delete or another Django event occurs.
→
2. Signal sent

→
3. Receiver runs
Your function handles the event.

Why use blog.apps.BlogConfig?
It ensures Django uses the app configuration class, whose ready() method imports the signals.
blog/signals.py
from django.db.models.signals import post_save, pre_save
from django.dispatch import receiver
from .models import BlogModel


@receiver(pre_save, sender=BlogModel)
def before_blog_save(sender, instance, **kwargs):
    print(f'About to save blog [pre-save]: {instance.title}')


@receiver(post_save, sender=BlogModel)
def after_blog_save(sender, instance, created, **kwargs):
    if created:
        print(f'New blog created [Post-Save]: {instance.title}')
    else:
        print(f'Blog updated [Post-Save]: {instance.title}')
blog/models.py
from django.db import models


class BlogModel(models.Model):
    title = models.CharField(max_length=100)
    content = models.TextField()
    author = models.CharField(max_length=50)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.title
blog/apps.py
from django.apps import AppConfig


class BlogConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'blog'

    def ready(self):
        import blog.signals
blog/admin.py
from django.contrib import admin
from .models import BlogModel


@admin.register(BlogModel)
class BlogModelAdmin(admin.ModelAdmin):
    list_display = ('title', 'author', 'created_at')
Note: The original example used class BlogModel(admin.ModelAdmin). It is clearer to name the admin class BlogModelAdmin so it is not confused with the model class.

Key point: The created argument in post_save tells you whether the save created a new database row. created=True means new object; created=False means an existing object was updated.

7. Real-World Example — Send Email When User Registers

This is a common signal use case. When a new user is created, a post_save receiver can detect created=True and send a welcome email.

from django.db.models.signals import post_save
from django.dispatch import receiver
from django.contrib.auth.models import User
from django.core.mail import send_mail


@receiver(post_save, sender=User)
def send_welcome_email(sender, instance, created, **kwargs):
    if created:
        send_mail(
            subject='Welcome to our website',
            message=f'Hello {instance.username}, welcome!',
            from_email='noreply@example.com',
            recipient_list=[instance.email],
        )
Production consideration: Sending email directly inside a model signal can make the save request wait for the email operation. For important or high-volume email, teams commonly move the work to a background task/queue system and keep the signal lightweight.

8. Common Developer Mistakes

1. Forgetting to import signals
If signals.py is never imported, the receivers may not be registered.
2. Wrong app configuration
Make sure the correct AppConfig is used and its ready() imports the signals module.
3. Using post_save when you need pre-save behavior
Choose the signal according to whether the logic belongs before or after the save.
4. Ignoring created
If an action should happen only for newly created objects, check created.
5. Putting heavy business logic in signals
Large hidden workflows can become difficult to trace. Keep signal handlers small and move complex workflows into explicit services/background jobs when appropriate.

9. Interview-Ready Explanation

How to explain Django Signals in an interview:

“Django Signals provide a way for one part of the application to react automatically when a particular event occurs. For example, pre_save runs before a model is saved and post_save runs after the save. I can use post_save with created=True to perform an action only when a new object is created, such as triggering a welcome email or creating a related profile. In my blog example, I register signal receivers and import the signals through the app's ready() method.”

Likely follow-up questions
  1. What is the difference between pre_save and post_save?
  2. Why do we use ready() in AppConfig?
  3. What does created=True mean?
  4. Can signals be used for sending emails?
  5. What are the risks of putting too much logic inside signals?
  6. What is the difference between a signal and directly calling a function?
