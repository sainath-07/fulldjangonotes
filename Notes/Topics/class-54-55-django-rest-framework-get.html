1. What is a REST API?

Definition

An API (Application Programming Interface) is a way for two programs to talk to each other.

A REST API is an API that works over the web using URLs and standard HTTP methods such as GET, POST, PUT, PATCH and DELETE. The server usually replies with data in JSON format.

Layman example

Think of a restaurant. You (the client) sit at the table and read the menu. You do not go into the kitchen. You tell the waiter what you want, and the waiter brings your food from the kitchen (the server).

The waiter is the API. The menu is the list of URLs you can ask for. The food that comes back is the JSON data.

Parts of one API call

PartMeaningExample
ClientThe app or website that asks for data.A mobile app, a React app, a browser
RequestThe question the client sends. It has an HTTP method and a URL.GET /api/students/
ServerThe program that receives the request and finds the data.Our Django project
ResponseThe answer. It has data (JSON) and a status code.A list of students, with status 200 OK

What is JSON?

JSON is a simple text format to write data as name and value pairs. It is easy for people to read and easy for programs to understand. Almost every language can read it.

{
  "id": 1,
  "name": "Asha",
  "age": 21,
  "city": "Pune"
}
Interview tip: Say it in one line: "A REST API lets a client ask a server for data using URLs and HTTP methods, and the server replies with JSON."

2. What is Django REST Framework (DRF)?

Definition

Django REST Framework is an add-on toolkit for Django. It helps us build web APIs quickly and in a clean way. It gives ready-made tools to turn database data into JSON, to handle requests, to check permissions, and more.

Layman example

Normal Django is like a restaurant that serves food only to guests sitting inside (web pages in a browser). DRF adds a takeaway counter with a ready-made packing system. Now delivery apps and other programs can also order and get their food in a standard box (JSON).

What does DRF give us?

FeatureWhat it doesUsed in this class?
SerializersConvert model data to JSON, and JSON back to data.Yes
API views (@api_view)Handle requests and send proper responses.Yes
Browsable APIA web page to test your API in the browser.Yes (automatic)
Authentication and permissionsControl who can use the API.Later
Pagination and filteringSend data in small pages, and search inside it.Later
Viewsets and routersWrite less code for full create, read, update, delete APIs.Later
Interview tip: DRF is not a separate framework. It is a package that works on top of Django, so we still use Django models, URLs and admin.

3. Why Use DRF?

Definition

We use DRF because it saves time and gives a standard way to build APIs. Many common jobs, like data conversion, checking input, security and testing, are already done for us.

Layman example

You can write every address on a hundred envelopes by hand. Or you can use a printer that does it in seconds and never makes a spelling mistake. DRF is the printer for API data.

Benefits

  • Less code: A serializer turns model data into JSON with just a few lines.
  • Browsable API: You can test your API in the browser without extra tools.
  • Built-in security tools: Ready-made authentication and permissions.
  • Input checking: Serializers can validate data sent by the client.
  • Grows with your project: Pagination, filtering and viewsets are ready when you need them.
  • Popular and well documented: Many companies use it, so help is easy to find.

Plain Django vs DRF

JobPlain DjangoWith DRF
Convert data to JSONDone by hand (dictionaries, JsonResponse)Serializer
Allow only some HTTP methodsCheck request.method yourself@api_view(['GET'])
Check incoming dataWrite your own checksSerializer validation
Login and permissions for the APIWrite your ownBuilt-in classes
Test page in the browserNoneBrowsable API
Honest note: For a very small read-only API, plain Django can also be short. DRF gives the most value as your API grows and needs create, update, delete, security and validation.

5. Where Does a REST API Lie?

Short answer: A REST API lies between the client and the server. It is the front door of the server. The server (our Django code) then talks to the database. The client never talks to the database directly.

Definition

The client sends a request to the API. The API passes the request to the server code. The server code reads or changes the database, and the API sends the result back to the client as a response.

Layman example

In a restaurant, the waiter stands between the customer and the kitchen. The customer never enters the store room (the database). The waiter and the kitchen handle it. The waiter (API) is the only way in.

Diagram: where the API sits

Why not let the client talk to the database directly?

  • Safety: Database passwords and rules stay hidden on the server.
  • Control: The API can check who is asking and what they may see or change.
  • Freedom to change: You can change the database later, and the client apps do not need to change.
  • One server, many clients: A website, an Android app and an iPhone app can all use the same API.
Interview tip: If asked "client and database, or client and server?", answer "client and server". Then add: "The server talks to the database on behalf of the client."

6. Difference: REST vs REST API

Definition

REST (Representational State Transfer) is a style of design, a set of rules for how web services should work. It was described by Roy Fielding in his PhD paper in the year 2000.

A REST API is a real API that follows those rules. It is also called a RESTful API.

Layman example

REST is like the rulebook of good restaurant service: greet the guest, show the menu, take the order, bring the food. A REST API is a real restaurant that follows this rulebook. You can walk in and order from it.

PointRESTREST API
What is it?An idea, a style, a set of rulesA working API built using those rules
Can you run it?No. It is not a tool or a program.Yes. It has real URLs you can call.
Who creates it?It is a concept, not made by a projectDevelopers build it (with Django and DRF)
Example"Use URLs for things, and GET to read them"GET /api/students/

The main REST rules

RuleMeaningLayman example
Client and server are separateThe app and the server work on their own. Many apps can use one server.Many customers, one kitchen.
StatelessEach request has all the information the server needs. The server does not remember the last request.You give your full order every time you call.
Uniform interfaceThings (resources) have URLs and use standard HTTP methods.Every restaurant uses a menu and a bill.
CacheableA response can say if it may be saved and reused.The daily special can be printed once.
Layered systemThe client does not need to know how many servers are behind the API.You do not know how many cooks are in the kitchen.
Good to know: DRF gives you the tools to build a REST API, but it does not force you to follow every rule. Following the rules is the developer's job.
Interview tip: "REST is the architecture style. A REST API is an API built by following that style."

api_app/models.py Model 
from django.db import models

# Create your models here.
class StudentModel(models.Model):
    name=models.CharField(max_length=100)
    age=models.IntegerField()
    city=models.CharField(max_length=100)

    def __str__(self):
        return self.name
  • Each object of this model is one row in the student table.
  • name and city store text (up to 100 characters). age stores a whole number and must be filled in.
  • Django also adds an id field by itself. It is the unique number of each student.
  • __str__ shows the student's name in the admin site.
api_app/admin.py Admin 
from django.contrib import admin
from .models import StudentModel

# Register your models here.
@admin.register(StudentModel)
class StudentAdmin(admin.ModelAdmin):
    list_display = ('id','name','age','city')
  • @admin.register shows the model in the admin site, so we can add test students easily.
  • list_display shows id, name, age and city as columns in the admin list.
api_app/serializers.py Serializer 
from rest_framework import serializers
from .models  import StudentModel

class StudentSerializer(serializers.ModelSerializer):
    class Meta:
        model=StudentModel
        fields='__all__'  # include all fields

Definition

A serializer converts Django model data into simple data (like JSON) that can be sent to the client. A ModelSerializer builds itself from the model, so we do not write each field again.

Layman example

A serializer is a translator. The database speaks "Python objects" and the client speaks "JSON". The translator changes one language into the other.

  • model = StudentModel tells the serializer which model to use.
  • fields = '__all__' includes every field: id, name, age, city. To pick only some, write a list, for example fields = ['id', 'name'].
api_app/views.py Most important file 
from django.shortcuts import render
from rest_framework.decorators import api_view
from .models import StudentModel
from .serializers import StudentSerializer
from rest_framework.response import Response

# Create your views here.
#GET view
@api_view(['GET'])
def student_list(request):
    students= StudentModel.objects.all()
    serializer = StudentSerializer(students, many=True)
    #many=True means we are giving a list of objects (many students), not just one.
    return Response(serializer.data)

A small correction to the class note

The original note says many=True means "many fields". That is not correct, so I changed the comment in the code above.

many=True means we are giving the serializer many objects (a list or a queryset), not one object. Fields are handled by fields = '__all__'. If you serialize a single student, for example StudentSerializer(student), you do not need many=True.

Line by line in simple words

CodeMeaning
@api_view(['GET'])Turns a normal function into a DRF API view, and allows only GET requests. Other methods, like POST, get a "405 Method Not Allowed" reply.
StudentModel.objects.all()Gets all students from the database.
StudentSerializer(students, many=True)Prepares to convert the list of students. many=True says it is a list.
serializer.dataThe converted result: a list of simple dictionaries, one for each student.
Response(serializer.data)Sends the data back to the client. DRF changes it to JSON, or to the browsable page in a browser. The default status is 200 OK.
Layman example: many=True is the difference between packing one gift and packing a box of gifts. Tell the packer it is a box, or it will not know how to pack them.
api_app/urls.py App URLs 
from . import views
from django.urls import  path

urlpatterns=[
    path('students/',views.student_list,name='student_list')
]
  • 'students/' is the address of this API. It runs the student_list view.
  • The full address is /api/students/, because the project urls.py adds the api/ part in front.
innerproject/urls.py Project URLs 
from django.contrib import admin
from django.urls import path,include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/',include('api.urls'))
]
  • admin/ opens the Django admin site.
  • api/ sends every URL that starts with api/ to the app's own urls.py.
  • Layman example: api/ is the street name and students/ is the house number. Together they give the full address.

Diagram: the journey of one GET request

10. Common Mistakes and Good Habits

Mistake 1: Forgetting 'rest_framework' in INSTALLED_APPS

Without it, the browsable page cannot find its template, and Django shows a TemplateDoesNotExist error for rest_framework/api.html.

Mistake 2: Wrong app name

If the name in INSTALLED_APPS or include() does not match the real folder, you get ModuleNotFoundError.

Mistake 3: Misspelled file name

A file named serlizers.py will not be found by from .serializers import .... Name it serializers.py.

Mistake 4: Forgetting many=True for a list

If you pass a queryset without many=True, Django shows an AttributeError about a field on the QuerySet.

Mistake 5: Forgetting migrations

If you skip makemigrations and migrate, the student table does not exist, and you will see a "no such table" error.

Mistake 6: Forgetting the api/ part of the URL

The correct address is /api/students/, not /students/. The api/ part comes from the project urls.py.

Watch out: fields = '__all__' shows everything

It is quick for learning. In real projects, list the fields you want to show, so private fields are not sent by mistake.

Watch out: this API is open to everyone

We have not added login or permissions yet. Anyone who knows the URL can read the list. Authentication and permissions are the next things to learn.

Good habits

  • Use plural names in URLs, like students/.
  • Keep serializers in their own file, serializers.py.
  • Test in the browsable API first, then in Postman or curl.
  • Read the error message. It usually names the exact file or field that is wrong.

11. Interview Questions and Answers

How to answer well: Give the definition first, then a small example, then one point about why it matters. Keep each answer to three or four sentences.

An API (Application Programming Interface) is a way for two programs to talk to each other. One program sends a request, and the other sends back a response.

It is a web API that follows REST rules. The client uses URLs and HTTP methods (GET, POST, PUT, PATCH, DELETE) to work with data, and the server usually replies in JSON.

REST is an architecture style, a set of rules. A REST API is a real API that follows those rules.

Between the client and the server. It is the front door of the server. The server code talks to the database, so the client never reaches the database directly. This keeps the data safe and lets many kinds of clients use one backend.

It is a toolkit built on top of Django for creating web APIs. It gives serializers, API views, authentication, permissions, pagination and a browsable API, so we write less code and follow a standard way.

A serializer converts Django model data (Python objects) into simple data like JSON, and it can also convert incoming JSON back into data and check it. We need it because a client cannot understand Python objects.

It makes a function-based view work as a DRF API view and allows only the listed HTTP methods. Any other method, such as POST, gets a 405 Method Not Allowed response.

It tells the serializer that we are giving it many objects (a queryset or a list), not just one. Without it, the serializer expects a single object and shows an error when it gets a queryset.

It includes every field of the model in the output. In real projects, we often list only the needed fields, for example fields = ['id', 'name'], so private data is not exposed.

Add 'rest_framework' to INSTALLED_APPS in settings.py. Then create serializers and views, and add URLs for them.

12. Quick Summary

Key points to remember
  • A REST API lets a client ask a server for data using URLs and HTTP methods. The reply is usually JSON.
  • REST is the style (rules). A REST API is a real API that follows the rules.
  • The API lies between the client and the server. The server talks to the database.
  • DRF is a toolkit on top of Django. Install it, and add 'rest_framework' to INSTALLED_APPS.
  • Build order: model, serializer, view, app URLs, project URLs.
  • many=True means "many objects", not "many fields".
  • Test at /api/students/. A GET reply is 200 OK.
