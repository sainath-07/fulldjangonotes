2. Template setup

A Django template is usually an HTML file. Django must know where to search for templates.

TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'],
        'APP_DIRS': True,
        'OPTIONS': {
            'context_processors': [
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',
                'django.contrib.messages.context_processors.messages',
            ],
        },
    },
]
Remember: DIRS can point to project-level template directories. APP_DIRS=True enables discovery of templates inside installed apps.
3. Rendering templates using views.py

A view creates data and passes it to a template using a context dictionary.

from django.shortcuts import render

def home(request):
    context = {
        "name": "Sainath",
        "age": 25,
        "course": "Django"
    }
    return render(request, "home.html", context)
<h1>Welcome {{ name }}</h1>
<p>Age: {{ age }}</p>
<p>Course: {{ course }}</p>
Easy rule: A context key becomes the template variable name. "name": "Sainath" is accessed as {{ name }}.
4. {{ variables }} basics

Template variables use double curly braces:

{{ variable_name }}

Example:

context = {
    "username": "Rahul",
    "age": 30
}
<h2>Name: {{ username }}</h2>
<p>Age: {{ age }}</p>
Important: Django template syntax is intentionally simpler than normal Python expressions.
Missing values: An unresolved ordinary template variable commonly renders as an empty string. Default filters can provide fallback text.
5. Dictionary, list, object & attribute access

Dictionary

context = {
    "user": {
        "name": "Amit",
        "email": "amit@example.com"
    }
}
{{ user.name }}

List

context = {
    "fruits": ["Apple", "Banana", "Mango"]
}
{{ fruits.0 }}
{{ fruits.1 }}
{{ fruits.2 }}
List indexes start from 0.

Object attribute

class User:
    def __init__(self, name):
        self.name = name

user = User("Priya")
context = {"user": user}
{{ user.name }}

Django's dot notation can resolve dictionary keys, object attributes, and list indexes according to its template variable lookup rules.

Memory: {{ user.name }}, {{ fruits.0 }} and similar dot lookups are common in templates.
6. Nested variables — {{ user.profile.name }}
context = {
    "user": {
        "profile": {
            "name": "Anil"
        }
    }
}
<h2>Name: {{ user.profile.name }}</h2>
user
→

→

→

Meaning: Django follows the value through multiple levels of dot lookup.
Mistake: The nested path must be resolvable. If an intermediate value cannot be resolved, output may be empty.
7. default & default_if_none

Without a filter

<h2>Value: {{ empty_value }}</h2>

default

default uses the fallback when the value is false/empty according to Django's template filter behavior.

<h2>
{{ empty_value|default:"Value is empty, so we show this text" }}
</h2>

default_if_none

default_if_none uses the fallback only when the value is None.

<h2>
{{ empty_value|default_if_none:"If value is None, we show this text" }}
</h2>

8. Safe vs autoescape

What is autoescape?

Django automatically escapes HTML-sensitive characters in normal variable output. This helps prevent untrusted content from being interpreted as HTML.

context = {
    "content": "<b>Welcome to Blog template page.</b>"
}

Without safe:

Content: {{ content }}

The HTML-looking value is escaped instead of being treated as a real <b> element.

Think of autoescape as protection: variable content is escaped by default so HTML markup is not automatically interpreted.

What is safe?

The safe filter marks a value as safe HTML, so Django does not escape it.

Content: {{ content|safe }}

If the value contains <b>Welcome to Blog template page.</b>, the browser can display:

Welcome to Blog template page.
Security warning: Never blindly use |safe on user-provided or untrusted HTML. Unsafe content can create XSS vulnerabilities.

escape

The escape filter explicitly escapes HTML-sensitive characters.

{{ content|escape }}
BehaviorPurpose
AutoescapeEscapes normal variable output by default.
safeTreats a value as safe HTML; use only for trusted content.
escapeEscapes HTML-sensitive characters.
9. Common developer mistakes
Wrong context key
View sends username, template uses user_name.
Wrong nested path
Using {{ user.profile.name }} when the required relationship does not exist.
Unsafe safe filter
Using |safe on untrusted user input.
Confusing defaults
Use default_if_none when only None should trigger the fallback.
Template not found
Check template location, DIRS, APP_DIRS, and installed apps.
Expecting Python syntax
Django templates have their own limited syntax; do not treat them like normal Python code.
