1. What is a Database Cache?

Definition

A cache is a place where we keep a ready-made copy of some data so we can get it quickly next time.

A database cache is a cache that keeps this saved data inside a table in your database. Django reads and writes this table for you.

Layman example

Think of a small office. Every time someone asks for the price list, the clerk walks to the big store room, searches the files, and brings it back. This takes time.

So the clerk keeps a small notebook in the same office and writes the answers there. Next time, the clerk just opens the notebook. The notebook is the database cache. It is kept in the same office (your database), so it is safe even if the clerk goes home for the day (server restart).

What is stored inside the cache table?

When you run the create-table command, Django makes a table with three columns:

ColumnWhat it holdsSimple meaning
cache_keyThe name of the saved item, for example user_listThe label on the notebook page
valueThe saved data (Django converts it to text form)The answer written on that page
expiresThe date and time when this item is no longer validThe "use before" date
Interview tip: Say it in one line: "A database cache stores cached data in a database table, so it survives restarts and needs no extra server."

2. When Should We Use a Database Cache?

Definition

Use caching when the same data is asked again and again, it does not change often, and it is slow or costly to fetch. Use a database cache when you want a simple setup without installing Redis or Memcached.

Layman example

A restaurant prints the menu of the day once and gives the same copy to every guest. That is a good use of caching. But each table's bill is different, so the waiter must not reuse one bill for all tables. Never cache data that is different for every person.

Good time to use it
  • The same page or list is opened many times.
  • The data changes rarely (blog posts, product lists, user lists).
  • The database query is heavy or slow.
  • You cannot install Redis or Memcached.
  • You want the cache to stay after a server restart.
  • Many server processes must share the same cache.
Time to avoid it
  • The data changes every second (live scores, stock prices).
  • The data is private and different for each user, and you use one shared key.
  • The query is already very fast and small.
  • You need the fastest possible speed. Use Redis or Memcached instead.

Which cache type should I pick?

Cache typeWhere data livesSpeedSurvives restart?Extra server needed?
Database cacheA table in your databaseMediumYesNo
Local memoryInside one Django processVery fastNoNo
File-basedFiles on diskMediumYesNo
Redis / MemcachedA separate cache serverFastestMemcached: no. Redis: depends on setupYes
Interview tip: Always mention the trade-off. Database cache is easy to set up, but it is slower than Redis or Memcached because each read is a database query.

3. How Does a Database Cache Work?

Definition

When a request comes in, the view first looks for a saved copy using a key.

  • Cache hit: the copy is found and still valid. Django returns it.
  • Cache miss: nothing found, or it has expired. Django reads the main data, saves a copy with a timeout, and returns it.

Layman example

You ask a friend for a phone number. If your friend has it written on a sticky note, they read it out at once (hit). If not, they look it up in the big phonebook, write it on a sticky note for next time, and tell you (miss). The sticky note is thrown away after 60 seconds, so the number stays fresh.

Diagram: request flow

Both paths end the same way: the view sends the data to the browser as a web page.

Step by step

  1. The browser opens /users/. Django runs the user_list view.
  2. The view calls cache.get('user_list'). Django looks in the cache table for this key.
  3. If the key is found and not expired, the saved data is returned. This is a cache hit.
  4. If not found, the view runs UserModel.objects.all() on the main table. This is a cache miss.
  5. The view saves the result with cache.set('user_list', data, timeout=60).
  6. After 60 seconds the saved copy expires, and the next request becomes a cache miss again.
Interview tip: Use the words "hit", "miss", "key" and "timeout" in your answer. It shows that you know the flow, not just the code.

4. Setup: Activate the Database Cache

To use the database cache, we need two things: tell Django about the cache in settings.py, and create the table in the database.

Step 1: Add the CACHES setting

Open innerproject/settings.py and add the code shown in the Code section. The value of LOCATION is the table name.

Step 2: Create the cache table

Run this command in your terminal. The general form is:

python manage.py createcachetable cachename

Use the same name you wrote in LOCATION. For our project it is:

python manage.py createcachetable my_cache_table
Watch the spelling: The file is manage.py, not mange.py. A small typo gives the error "can't open file".

Definition

cachename must match the LOCATION value in settings.py. If they are different, Django will look for a table that does not exist.

Layman example

It is like writing a name on a locker and then going to the same locker later. If you wrote "locker A" on the form but go to "locker B", you will find it empty.

Step 3: Prepare the demo project

These are the normal Django commands needed for the example app (models, admin and server):

python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver

Then open http://127.0.0.1:8000/admin/, log in, and add a few users in the User models section. Now open http://127.0.0.1:8000/users/.

Good to know: If you run python manage.py createcachetable without a name, Django creates the tables for all database caches listed in CACHES.

blog_app/views.py Most important file 
from django.shortcuts import render,redirect
from .models import UserModel
from django.core.cache import cache

# Create your views here.
def user_list(request):
    userlist= cache.get('user_list')

    if not userlist:
        print('cache not hit')
        userlist=UserModel.objects.all()
        cache.set('user_list',userlist,timeout=60) #60 seconds timeout cache
    else:
        print('cache hit: ')

    return render(request,'user_list.html',{'users':userlist})

def clear_cache(request):
    cache.clear()
    print('cleared cache successfully...')
    return redirect('user_list')

6. See It Working: Demo Walkthrough

Watch the terminal where runserver is running. The print() lines tell you if the cache was used.

#What you doTerminal showsWhat it means
1Open /users/ for the first timecache not hitNothing was saved yet, so Django read the main table and saved a copy.
2Refresh within 60 secondscache hit:Data came from the cache table.
3Add a new user in admin, then refresh /users/cache hit:The new user is not shown. The page still uses the old saved copy.
4Wait 60 seconds and refreshcache not hitThe copy expired, so Django read fresh data. The new user now appears.
5Click Clear cachecleared cache successfully... then cache not hitAll saved items were deleted. The page reloads and saves a fresh copy.

Diagram: what happens over time

0 s: Miss (save copy) → 1 to 59 s: Hit, Hit, Hit → 60 s: Copy expires → Next request: Miss (save new copy)
Layman example: A newspaper printed at 8 AM will not show the news that happened at 9 AM. You must wait for the next print. In the same way, cached data can be a little old until it expires or you clear it. This is the main trade-off of caching: speed in exchange for freshness.

7. Cache Methods Cheat Sheet

MethodWhat it doesUsed in class?
cache.get(key)Reads a saved value. Returns None if it is missing or expired.Yes
cache.set(key, value, timeout)Saves a value for the given number of seconds.Yes
cache.clear()Removes every item from the cache.Yes
cache.delete(key)Removes just one item.Extra
cache.get_or_set(key, default, timeout)Gets the value, or saves and returns the default if missing.Extra

About timeout

If you do not give a timeout, Django uses the default of 300 seconds (5 minutes). If you set timeout=None, the item never expires.

Layman example

A delete is like removing one sticky note. A clear is like emptying the whole notice board.

8. Common Mistakes and Good Habits

Mistake 1: Different table names

The name in LOCATION and the name in createcachetable must be the same. If not, you will see an error like "no such table".

Mistake 2: Forgetting to create the table

Adding CACHES in settings is not enough. You must also run createcachetable.

Mistake 3: Expecting instant updates

When data changes, the cache still shows the old copy until it expires. Use a short timeout, or delete the key when the data changes.

Watch out: An empty list looks like a miss

The line if not userlist: is also true when the list is empty. So if there are no users, every request will be a cache miss. A more exact check is if userlist is None:.

Watch out: Unclosed HTML in the template

In the template, the <p>No users found.</p> line sits inside <tbody>. Browsers may move it outside the table. A cleaner way is to put it inside a table row: <tr><td colspan="2">No users found.</td></tr>.

Good habits

  • Use clear key names such as user_list.
  • Choose a timeout that matches how often the data changes.
  • Never cache private data under a key shared by all users.
  • Test both a hit and a miss, using print lines or logs.

9. Interview Questions and Answers

How to answer well: Give the definition first, then a small example, then one trade-off. Keep each answer to three or four sentences.

It is a cache backend that stores saved data in a database table. Django reads from this table to avoid repeating slow queries or heavy work. It is easy to set up because it needs no extra server.

First, set BACKEND to django.core.cache.backends.db.DatabaseCache and set LOCATION to a table name in CACHES. Then run python manage.py createcachetable table_name.

For a database cache, it is the name of the table where cached data is stored. It must match the name used in the createcachetable command.

A hit means the data was found in the cache and returned quickly. A miss means the data was not found or had expired, so the app fetched it from the main source and saved a new copy.

It returns None. You can also pass a second value as a default, for example cache.get('key', 'default').

A database cache is simple and needs no extra server, and its data stays after a restart. But it is slower, because every read is a database query. Redis and Memcached keep data in memory on a separate server, so they are faster, but they need extra setup.

Use a short timeout, or delete the cache key whenever the data changes (for example after saving a new record). You can also clear the whole cache with cache.clear(), but this removes every item, so use it carefully.

10. Quick Summary

Key points to remember
  • Database cache keeps saved data in a database table.
  • Use it for data that is read often and changes rarely.
  • LOCATION in settings = the table name.
  • Create the table with createcachetable.
  • get to read, set to save, clear to remove all.
  • After the timeout, the copy expires and is rebuilt on the next request.
