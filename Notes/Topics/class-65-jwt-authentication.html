1. What is JWT Authentication in Django?

JWT (JSON Web Token) Authentication is a stateless authentication mechanism where the server issues a signed token — containing encoded user claims (like user ID, expiry time) — instead of storing session data. In Django, this is implemented using the djangorestframework-simplejwt package (rest_framework_simplejwt).

A JWT has three parts, separated by dots:

header.payload.signature

The client sends the JWT in the Authorization header on each request:

Authorization: Bearer <access_token>
The server never needs to store the token — it just verifies the signature and expiry. This makes JWT auth stateless and scalable across multiple servers.
2. What is Access Token and Refresh Token?
Access Token

A short-lived token sent with every API request to prove identity and access protected resources.

  • Short lifetime (e.g. 5 minutes by default in simplejwt)
  • Sent in Authorization: Bearer header
  • Used directly to access protected views
Short lifetime
Refresh Token

A longer-lived token used only to obtain a brand-new access token once the old one expires — via TokenRefreshView.

  • Longer lifetime (e.g. 1 day by default in simplejwt)
  • Sent only to /api/token/refresh/
  • Not used directly to access protected views
Longer lifetime
3. Key Questions Answered
Is normal JWT authentication in Django and JWT integrated in other backend applications like Node.js or Java different?
No — the underlying concept is the same. JWT is an open standard (RFC 7519), so the token structure (header.payload.signature), signing algorithms (HS256/RS256), and the idea of stateless verification work identically across Django, Node.js, Java, or any other backend. What differs is only the library/implementation used to generate and verify tokens — Django commonly uses djangorestframework-simplejwt, Node.js might use jsonwebtoken, and Java might use jjwt or Spring Security's JWT support. The token itself is fully interoperable across languages.
Does the access token expire first, or does the refresh token expire first?
The access token expires first. Access tokens are intentionally short-lived (minutes) to limit damage if leaked, while refresh tokens live much longer (hours/days) so the user isn't forced to log in again frequently. When the access token expires, the client uses the still-valid refresh token to silently obtain a new access token.
4. When to Use JWT Authentication
  • Single Page Applications (React, Angular, Vue) calling a separate API backend
  • Mobile apps needing stateless, scalable authentication
  • Microservices architectures where multiple services need to verify identity without shared session storage
  • Cross-domain APIs consumed by third-party clients
  • Avoid if you need instant server-side token revocation without extra blacklisting setup — JWTs remain valid until expiry unless you implement a token blacklist
5. JWT Flow Diagram

Login → Access + Refresh Tokens → Refresh Cycle


POST /api/token/
username & password

TokenObtainPairView
returns access + refresh

Bearer <access_token>
on API requests
Access token expires (short-lived)

POST /api/token/refresh/
send refresh_token

TokenRefreshView
issues new access token

Cycle repeats until the refresh token itself expires (longer-lived) — then the user must log in again.

blog/views.py
from rest_framework.response import Response
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticatedOrReadOnly

@api_view(['GET', 'POST'])
@permission_classes([IsAuthenticatedOrReadOnly])
def post_list(request):
    if request.method == 'GET':
        return Response({'message': "Public can view this data"})
    elif request.method == "POST":
        return Response({'message': f'Data created by {request.user.username}'})
blog/urls.py
from .  import views
from django.urls import path

urlpatterns=[
    path('posts/',views.post_list,name="post_list")
]
Note: post_list uses IsAuthenticatedOrReadOnly — so GET is public, while POST requires a valid JWT access token to identify request.user.
7. Interview Tips
1Know the 3 parts of a JWT.

Header (algorithm & type), Payload (claims like user id, exp), and Signature (verifies integrity). The payload is Base64-encoded, not encrypted — never put secrets in it.

2Be ready to explain the refresh cycle.

Access token expires quickly → client silently calls the refresh endpoint with the refresh token → gets a new access token → user experience stays uninterrupted until the refresh token itself expires.

3Common trick question:

"Is Django's JWT different from Node.js/Java JWT?" — Answer confidently: No, JWT is a language-agnostic standard; only the library used to sign/verify differs.

4Mention JWT revocation trade-offs.

Since JWTs are stateless, you can't instantly invalidate one without extra infrastructure (e.g. a token blacklist / denylist stored server-side), unlike session authentication where deleting the session immediately logs the user out.

5Compare JWT vs Token Authentication vs Session Authentication.

JWT: stateless, self-contained, has expiry + refresh mechanism. DRF Token: stateless but stored in DB, no built-in expiry. Session: stateful, cookie-based, needs CSRF protection.
