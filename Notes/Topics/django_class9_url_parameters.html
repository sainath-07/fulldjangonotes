App folder — where should urls.py live?

A Django project contains the main configuration, while a Django app contains a feature or part of the application. For normal app-level routing, create urls.py inside the app folder.

Simple rule: The project URL file decides which app handles a URL. The app URL file decides which view handles the URL inside that app.
URL parameters

What are URL parameters?

URL parameters are dynamic values placed inside a URL. Instead of creating a separate URL for every user or product, one URL pattern can handle many values.

blog/1
blog ID = 1
blog/2
blog ID = 2
products/101
product ID = 101
Why? A dynamic URL avoids writing hundreds of hard-coded routes such as blog/1, blog/2, blog/3...

Three concepts used in this lesson

  1. path() — the normal and recommended way to create URL patterns.
  2. re_path() — uses regular expressions when the URL rule is more complex.
  3. kwargs — a Python dictionary of named values passed from the URL resolver to a view. It is not itself a URL-routing function.
path(), re_path(), and kwargs — what, why, and how?

path()

What: Django's readable URL pattern helper.

Why: Use it for most normal dynamic routes.

How: Put a converter and variable name inside <...>.

path("name/<str:user_name>",
     views.username)

re_path()

What: A URL pattern helper that accepts a regular expression.

Why: Use it when a pattern needs regex-level matching.

How: Write the regex and capture named groups.

re_path(
 r"^article/(?P<year>[0-9]{4})/"
 r"(?P<month>[0-9]{2})/$",
 views.dob
)

kwargs

What: A dictionary containing named URL values.

Why: It lets a view accept several named values without declaring each one separately.

How: Django can call the view with keyword arguments such as productid and productname.

def productDetails(request, **kwargs):
    return HttpResponse(
      f"productDetails: {kwargs}"
    )

Interview point: Prefer path() when a converter can express the requirement. Reach for re_path() when you genuinely need regular-expression matching.
How does the dynamic variable name work?

In <int:user_id>, int is the converter and user_id is the variable name. Django captures the value from the URL and sends it to the view using that name.

path("userDetails/<int:user_id>/<str:user_name>",
     views.userDetails)
/userDetails/25/Sai
→
user_id = 25
user_name = "Sai"
→
views.userDetails(request, user_id=25, user_name="Sai")
Names must match: If the route uses <str:user_name>, the view must accept user_name (or use **kwargs). Changing the route name to <str:name> while leaving the view as user_name causes an argument mismatch.
Project main urls.py — class-based import syntax

The main project urls.py can connect an app's URL configuration with include(). You can also import a class-based view directly and pass the result of .as_view() to path().

Recommended app include

from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("myapp.urls")),
]

Class-based view import syntax

# project/urls.py

from django.contrib import admin
from django.urls import path, include
from myapp.views import UserDetailView

urlpatterns = [
    path("admin/", admin.site.urls),
    path("user/<int:user_id>/",
         UserDetailView.as_view(),
         name="user-detail"),
]
Remember: For a class-based view, URL configuration normally uses ClassName.as_view(), not just ClassName. If you keep routes inside the app, import the app URL module with include("myapp.urls").
Complete working example

1. views.py

from django.http import HttpResponse

def home(request):
    return HttpResponse("Welcome to Home page...")

def username(request, user_name):
    return HttpResponse(
        f'<h2>user page, user name: {user_name}</h2>'
    )

def userDetails(request, user_name, user_id):
    return HttpResponse(
        f'<h2>User Details of user name and user id - '
        f'user_name:{user_name}, user_id: {user_id}</h2>'
    )

def productDetails(request, **kwargs):
    return HttpResponse(
        f'productDetails page with kwargs: {kwargs}'
    )

def dob(request, year, month):
    return HttpResponse(
        f'<h2>dob: year:{year} month:{month} </h2>'
    )

2. app/urls.py

from . import views
from django.urls import path, re_path

urlpatterns = [
    path("", views.home, name="home"),

    # Handling a single dynamic route with path.
    path("name/<str:user_name>",
         views.username,
         name="user_name"),

    # Handling multiple dynamic routes with path.
    path("userDetails/<int:user_id>/<str:user_name>",
         views.userDetails,
         name="userDetails"),

    # Passing multiple dynamic routes and handling with kwargs.
    path("productdetails/<int:productid>/<str:productname>/",
         views.productDetails,
         name="productDetails"),

    # Complex dynamic path with re_path.
    re_path(
        r"^article/(?P<year>[0-9]{4})/"
        r"(?P<month>[0-9]{2})/$",
        views.dob,
        name="dob"
    ),
]

3. project/urls.py

from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("myapp.urls")),
]
Small correction from the original example: kwargs is the correct spelling. The original code/comment used kwars in a few places. The variable name kwargs is conventional and clearer.

Common developer mistakes
1. Wrong variable name
Route: <int:user_id>
View: def userDetails(request, id):

These names do not match.
2. Wrong converter
<int:user_id> will not match a non-integer value such as abc.
3. Forgetting slashes
Be consistent with the URL pattern and understand whether your project uses a trailing slash.
4. Calling a class directly
For a class-based view, use MyView.as_view() in the URL pattern.
5. Using regex when path() is enough
Do not make a simple route harder to read without a reason.
6. Thinking kwargs is a routing method
kwargs is how named keyword values can be received by the view. path() and re_path() define the route.
Interview tips & quick revision
One-line answer: Django URL parameters make routes dynamic by capturing values from the URL and passing those values to the view as named arguments.
  • path() is the usual choice for dynamic routes.
  • re_path() is useful when regular-expression matching is required.
  • The name inside <...> becomes the keyword argument name.
  • <int:id> converts the captured value to an integer before the view receives it.
  • **kwargs collects named keyword arguments into a dictionary.
  • For class-based views, use MyView.as_view() in path().
