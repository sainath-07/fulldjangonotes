1. Overview: what are we building?

In classes 55 to 58 we build a complete CRUD API with Django REST framework (DRF). CRUD means Create, Read, Update and Delete. These are the four basic actions almost every application performs on its data.

Layman example: the school register

Think of a school office register. The clerk can add a new student (Create), look up a student (Read), correct a wrong phone number (Update), or remove a student who left (Delete). Our API does the same work, but for a computer or a mobile app instead of a person.

3. What is a serializer?

Definition

A serializer is a DRF class that does two jobs. First, it converts Django model objects (and querysets) into simple Python data that can be sent as JSON. Second, it takes incoming JSON data, checks it, and converts it back into a form Django can save in the database.

Layman example 1: the translator

Your database speaks "Django objects". A mobile app or website speaks "JSON". They cannot understand each other directly. The serializer stands between them like a translator: it translates in both directions and also checks that nothing wrong is being said.

Layman example 2: packing a parcel

When you send a parcel, you pack the items in a box. That is serialization. When the parcel arrives, the receiver opens the box and checks every item against the list. That is deserialization plus validation. The serializer is the person who packs, opens and checks.

If you know JavaScript

A serializer is like JSON.stringify and JSON.parse combined with a validation schema (similar to Yup or Zod). It converts the data and also checks it.

What does a serializer do?

Serialization
Turns a model object or queryset into Python data (and then JSON). Used in GET requests, when we send data out.
Deserialization
Turns incoming JSON data into Python data. Used in POST, PUT and PATCH requests, when we take data in.
Validation
Checks the incoming data: are all required fields present, is the type correct (a number where a number is needed), is the text too long, is the email unique?
Saving
With serializer.save() it creates a new record or updates an existing one in the database.

How does it work?

A. Reading data (GET): database to JSON

DatabaseStudent rows
Model objectsStudentModel
SerializerReads each field
serializer.dataPython dictionary
ResponseJSON to client

B. Writing data (POST, PUT, PATCH): JSON to database

ClientSends JSON
request.dataParsed by DRF
Serializerdata=request.data
is_valid()Checks the data
save()Writes to the database

If is_valid() fails, nothing is saved. The serializer keeps the problems in serializer.errors, and the view sends them back with status 400.

Same data, three forms

what the serializer converts
# 1. A model object (what the database gives us)
student = StudentModel(id=1, name='Ravi', age=21)

# 2. After the serializer (serializer.data): a Python dictionary
{'id': 1, 'name': 'Ravi', 'age': 21}

# 3. After Response(...): JSON text sent over the internet
# {"id": 1, "name": "Ravi", "age": 21}

Give a one-line answer first: "A serializer converts complex data like model objects to JSON and back, and it also validates incoming data." Then add the parcel or translator example. Interviewers like short definitions followed by a simple example.

4. Model and serializer files

Note

The demo code shared with these notes does not include models.py and serializers.py. The files below are a typical example so that the demo can run. Use the fields from your own class code.

api/models.py (example)
from django.db import models

class StudentModel(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()
    email = models.EmailField(unique=True)

    def __str__(self):
        return self.name
api/serializers.py (example)
from rest_framework import serializers
from .models import StudentModel

class StudentSerializer(serializers.ModelSerializer):
    class Meta:
        model = StudentModel
        fields = '__all__'
terminal
python manage.py makemigrations
python manage.py migrate
python manage.py runserver

Line by line

  • ModelSerializer is a shortcut. It reads your model and creates the serializer fields for you. It also gives you ready-made create() and update() methods.
  • class Meta holds the settings for the serializer.
  • model = StudentModel tells the serializer which model to use.
  • fields = '__all__' means "include every field of the model". You can also give a list, such as ['id', 'name'], to send only some fields.
Layman example

A plain Serializer is like writing every field on a form by hand. A ModelSerializer is like printing the form automatically from a template you already have, which is your model.

🎯 Interview tip

Question: "Serializer or ModelSerializer?" Answer: "ModelSerializer writes less code because it builds the fields and the create and update methods from the model. I use a plain Serializer when the data does not match a model exactly."

5. URL routing

The URL file decides which view runs for which address. Each path() has three parts: the address, the view function, and a name.

api_app/urls.py
from . import views
from django.urls import path

urlpatterns = [
    path('students/', views.student_list, name='student_list'),
    path('get_student/<int:pk>/', views.get_student, name='get_student'),
    path('add_student/', views.add_student, name='add_student'),
    path('delete_student/<int:pk>/', views.delete_student, name='delete_student'),
    path('update_student/<int:pk>/', views.update_student, name='update_student'),
]
What is <int:pk>?

pk means primary key, which is the unique id of a record. int means only whole numbers are allowed. So get_student/5/ works, but get_student/abc/ does not match and gives a 404 error.

Layman example

pk is like a student's roll number. To find one student in a big register, you do not say the name. You say the roll number, because it is unique.

🎯 Interview tip

In this demo the action is written in the URL (add_student, delete_student). This is good for learning. In real REST design, the URL names the resource (/students/ and /students/5/) and the HTTP method says the action. DRF ViewSets and routers build such URLs automatically. Mentioning this shows you know the next step.

What does @api_view do?

The @api_view(['GET']) decorator does three things. It allows only the HTTP methods you list (other methods get a 405 error). It gives you a DRF request object with request.data. And it lets you return a DRF Response.

Layman example

It works like a security guard at the office door. The guard has a list that says "only visitors with an appointment for this counter may enter". Anyone else is politely sent away.

GET 7. Read all students

This view returns the full list of students. It is the "Read" part of CRUD.

api_app/views.py
@api_view(['GET'])
def student_list(request):
    students = StudentModel.objects.all()
    serializer = StudentSerializer(students, many=True)
    return Response(serializer.data)

Step by step

  1. StudentModel.objects.all() gets every student from the database. The result is called a queryset (a list-like collection of objects).
  2. StudentSerializer(students, many=True) converts all of them into Python data.
  3. Response(serializer.data) sends the data back as JSON.
A small correction about many=True

The class comment says many=True means "many fields". That is not correct. many=True means many objects, in other words a list or queryset of students. The serializer already knows all the fields from its Meta class.

Use many=True when you pass a queryset. Do not use it when you pass a single object.

Layman example

One student's admission form is a single object. The whole class register has many students. many=True tells the serializer: "This is the full register, so please handle every row."

Sample response (status 200 OK)

JSON
[
  { "id": 1, "name": "Ravi",  "age": 21, "email": "ravi@example.com" },
  { "id": 2, "name": "Anita", "age": 22, "email": "anita@example.com" }
]
🎯 Interview tip

Question: "What happens if you forget many=True with a queryset?" Answer: "The serializer expects one object, so it raises an error or gives wrong output. A queryset needs many=True."

GET 8. Read one student

This view returns one student. The id comes from the URL, for example get_student/1/.

api_app/views.py (class version)
@api_view(['GET'])
def get_student(request, pk):
    student = StudentModel.objects.get(id=pk)
    serializer = StudentSerializer(student)
    return Response(serializer.data)

Here there is no many=True, because we give the serializer only one object.

What if the student does not exist?

.get() raises a DoesNotExist error when nothing matches. In the code above nobody catches it, so the API crashes with a 500 server error instead of a friendly message.

Better version: handle the missing student and return 404, exactly as the update and delete views do.

api_app/views.py (improved)
@api_view(['GET'])
def get_student(request, pk):
    try:
        student = StudentModel.objects.get(id=pk)
    except StudentModel.DoesNotExist:
        return Response({'error': 'student not found'}, status=status.HTTP_404_NOT_FOUND)

    serializer = StudentSerializer(student)
    return Response(serializer.data)
🎯 Interview tip

Say that a good API never lets the user see a server crash. It returns a clear 404 for "not found". You can also mention the shortcut get_object_or_404() from Django.

POST 9. Create a student

This view receives new student data from the client, checks it, and saves it. It is the "Create" part of CRUD.

api_app/views.py
@api_view(['POST'])
def add_student(request):
    serializer = StudentSerializer(data=request.data)
    if serializer.is_valid():
        serializer.save()
        return Response(serializer.data, status=status.HTTP_201_CREATED)
    return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

Step by step

  1. The client sends JSON in the request body. DRF reads it into request.data.
  2. StudentSerializer(data=request.data) gives the data to the serializer. The word data= is important. It tells the serializer "this is new data to check".
  3. is_valid() runs all the checks.
  4. If valid, save() adds a new row to the database. We return the saved data with status 201 Created.
  5. If not valid, we return serializer.errors with status 400 Bad Request.
Layman example: the bank counter

You fill a form and give it to the bank clerk. The clerk checks it first: is the name written, is the phone number correct? If everything is fine, the clerk files it (201 Created). If something is missing, the clerk hands it back with remarks (400 Bad Request). The clerk never files a wrong form.

Request body
{
  "name": "Ravi",
  "age": 21,
  "email": "ravi@example.com"
}
Success: 201 Created
{
  "id": 3,
  "name": "Ravi",
  "age": 21,
  "email": "ravi@example.com"
}
Failure: 400 Bad Request (email was missing, age was not a number)
{
  "age": ["A valid integer is required."],
  "email": ["This field is required."]
}
🎯 Interview tip

Remember the pattern: serializer with data, is_valid, save, Response. Explain why 201 is used for a successful create (not 200), and why 400 is used for wrong input.

PUTPATCH 10. Update a student

This view changes an existing student. One view handles both PUT and PATCH, and it uses request.method to see which one was used.

api_app/views.py (corrected)
@api_view(['PUT', 'PATCH'])
def update_student(request, pk):
    try:
        student = StudentModel.objects.get(id=pk)
    except StudentModel.DoesNotExist:
        return Response({'error': 'student not found'}, status=status.HTTP_404_NOT_FOUND)

    if request.method == 'PATCH':
        serializer = StudentSerializer(student, data=request.data, partial=True)
    else:
        serializer = StudentSerializer(student, data=request.data)

    if serializer.is_valid():
        serializer.save()
        return Response(serializer.data, status=status.HTTP_200_OK)
    return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)
Bug fixed in the last line

In the class code, the last line was status=HTTP_400_BAD_REQUEST. That name does not exist on its own, so Python raises a NameError the moment invalid data is sent. The correct form is status=status.HTTP_400_BAD_REQUEST, with the status. prefix.

The most important idea: passing the existing object

Look at StudentSerializer(student, data=request.data). The first argument is the existing student. Because of this, save() knows it must update that record. In the POST view there was no existing object, so save() created a new one.

How the serializer is createdWhat save() does
StudentSerializer(data=...)Creates a new record (INSERT)
StudentSerializer(student, data=...)Updates the existing record (UPDATE)

Layman example

PUT is like tearing out a page of your notebook and writing the whole page again. PATCH is like taking a pen and correcting one wrong word on the same page.

PUT request body (all fields)
{
  "name": "Ravi Kumar",
  "age": 22,
  "email": "ravi@example.com"
}
PATCH request body (one field)
{
  "age": 22
}
🎯 Interview tip

Two favourite questions: "PUT vs PATCH?" and "How does save() know whether to create or update?" The answers are in the two tables above. Also say what partial=True does: it makes all fields optional for that request.

DELETE 11. Delete a student

This view removes a student from the database. It is the "Delete" part of CRUD.

api_app/views.py
@api_view(['DELETE'])
def delete_student(request, pk):
    try:
        student = StudentModel.objects.get(id=pk)
    except StudentModel.DoesNotExist:
        return Response({'error': 'student not found'}, status=status.HTTP_404_NOT_FOUND)

    student.delete()
    return Response({'message': 'student deleted successfully'}, status=status.HTTP_204_NO_CONTENT)

Step by step

  1. Find the student by pk. If there is none, return 404.
  2. student.delete() removes the row from the database.
  3. Return a success response.

Notice that no serializer is needed here. We are not converting or checking any data, we are only removing a record.

About status 204

204 No Content means "the job is done and I have nothing to send back". By HTTP rules a 204 response has no body, so the message student deleted successfully may never reach the client. If you want the client to see the message, return status.HTTP_200_OK instead. If you keep 204, send an empty Response(status=status.HTTP_204_NO_CONTENT).

Layman example

A student leaves the school, and the clerk crosses the name out of the register. If the name is not in the register at all, the clerk says "no such student" (404).

🎯 Interview tip

Good to know: in real projects, many teams do a soft delete. They mark the record as inactive instead of removing it, so the data can be recovered later.

2xx means success. 4xx means the client made a mistake. 5xx means the server made a mistake.

13. How to test the APIs

Start the server with python manage.py runserver. You can then test the endpoints in three ways.

  • Browser: open http://127.0.0.1:8000/students/. DRF shows a readable page called the browsable API. GET URLs work directly.
  • Postman or Thunder Client: best for POST, PUT, PATCH and DELETE. For POST and PUT, choose Body, then raw, then JSON.
  • curl: use the commands below in a terminal.
terminal (curl)
# Read all
curl http://127.0.0.1:8000/students/

# Read one
curl http://127.0.0.1:8000/get_student/1/

# Create
curl -X POST http://127.0.0.1:8000/add_student/ \
  -H "Content-Type: application/json" \
  -d '{"name":"Ravi","age":21,"email":"ravi@example.com"}'

# Update everything (PUT)
curl -X PUT http://127.0.0.1:8000/update_student/1/ \
  -H "Content-Type: application/json" \
  -d '{"name":"Ravi Kumar","age":22,"email":"ravi@example.com"}'

# Update one field (PATCH)
curl -X PATCH http://127.0.0.1:8000/update_student/1/ \
  -H "Content-Type: application/json" \
  -d '{"age":22}'

# Delete
curl -X DELETE http://127.0.0.1:8000/delete_student/1/
Tip for Windows Command Prompt

Single quotes around JSON do not work in Command Prompt, and the \ line breaks are for Linux and Mac. On Windows, use Postman, or put the whole command on one line with double quotes escaped like \".

15. Interview questions and answers

A serializer converts model objects and querysets into Python data that can be sent as JSON. It also converts incoming JSON into validated Python data that can be saved in the database. Example: it is a translator and a checker between the database and the client.

Serialization converts an object into JSON-ready data (used in GET). Deserialization converts incoming JSON into Python data (used in POST, PUT and PATCH). Memory trick: serialize means send out, deserialize means take in.

With Serializer you declare each field yourself and write create() and update(). With ModelSerializer, DRF builds the fields from the model and gives you default create() and update(). It means less code.

It tells the serializer that it receives a list or queryset of objects instead of one object. It is about the number of objects, not the number of fields.

is_valid() runs the checks on the incoming data. DRF forces you to call it: if you call save() first, it raises an assertion error. This protects the database from bad data.

PUT replaces the whole record, so all required fields must be sent. PATCH updates only the fields you send. In DRF, PATCH is done with partial=True.

If the serializer was created with an existing object (StudentSerializer(student, data=...)), save() calls update(). If there is no existing object, it calls create().

It converts a normal function into a DRF API view. It restricts the allowed HTTP methods, provides request.data, and lets us return a DRF Response.

DRF's Response chooses the output format based on what the client asks for. It can give JSON to an app and the browsable API page to a browser. It also works smoothly with status codes.

200 for a successful read or update, 201 for create, 204 for delete (no content), 400 for invalid data, and 404 when the record is not found.

Function-based views (like ours) are simple and easy to read, which is good for learning. Class-based views, generic views and ViewSets reduce repeated code, and routers can create the URLs automatically. Large projects usually prefer ViewSets.

16. Quick revision

Patterns to remember
  • GET all: .all(), serializer with many=True, Response
  • GET one: .get(id=pk), serializer, Response
  • POST: data=request.data, is_valid(), save(), 201
  • PUT / PATCH: pass the object and data, PATCH uses partial=True
  • DELETE: find the object, .delete(), Response
Golden rules
  • Register api and rest_framework in settings.
  • Always use data= for incoming data.
  • Always call is_valid() before save().
  • Handle "not found" with a 404, never a crash.
  • Use status. before every status name.
