In-Memory Cache — LocMemCache

Store frequently used data in RAM so Django can return it faster instead of querying the database every time.

1. Class Overview

Topic: In-memory caching using Django's LocMemCache.

Main idea: If the same data is requested repeatedly, keep a temporary copy in memory and reuse it instead of querying the database every time.
2. What is Cache?
Definition

A cache is temporary storage used to keep frequently requested data so an application can retrieve it faster.

Layman example

If you use the same book many times, keeping it on your desk is faster than going to the library every time. The desk copy is like a cache.

User Request
→
Check Cache
→
Return if available
Benefit: Faster responses and fewer repeated database reads.
3. What is In-Memory Cache?
Definition

In-memory caching means storing temporary application data in RAM instead of reading it from the database or disk every time.

Layman example

RAM is like your work desk. The database is like a storage room. Taking something from the desk is usually quicker than walking to the storage room.

Django
↔
RAM
LocMemCache
↔
Database
Remember: Cache is temporary. The database remains the persistent source of data.
4. Simple Example
First request: Cache miss → query database → save result in cache → return data.
Second request: Cache hit → return cached result → database query is avoided.
After timeout: Cache entry expires → query database again → save fresh result.
5. CACHES Configuration — settings.py

In innerproject/settings.py:

CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.locmem.LocMemCache',
        'LOCATION': 'unique-snowflake'
    }
}
What is BACKEND?

BACKEND tells Django which cache implementation to use. Here it is LocMemCache, which stores cache data in local process memory.

What is LOCATION?

LOCATION is an identifier/name for the local-memory cache. 'unique-snowflake' is not a physical folder or database table.

Easy memory trick:
BACKEND = Which cache implementation?
LOCATION = What identifies this local cache?
Interview tip: With LocMemCache, the cache is local to the process/server rather than a shared external cache service.

8. View — Cache Hit and Cache Miss

youtube_app/views.py

from django.shortcuts import render
from django.core.cache import cache
from .models import YoutubeModel

def users_list(request):
    users = cache.get('user_list')

    if not users:
        users = YoutubeModel.objects.all()
        cache.set('user_list', users, timeout=60)
        print('cache not hit: getting data from database')
    else:
        print('Cache hit: fetching data from cache')

    return render(request, 'users_list.html', {'users': users})
How it works
1. cache.get() — Check whether user_list exists in cache.
2. Cache miss — Query YoutubeModel.objects.all().
3. cache.set() — Store the result for 60 seconds.
4. Cache hit — Reuse the cached result.
5. render() — Send users to the template.
Note: For simple examples, if not users is common. In production, think carefully about whether an empty result should count as a cache miss and use an explicit cache check when needed.

10. Clear User Cache from Django Admin

youtube_app/admin.py

from django.contrib import admin
from django.core.cache import cache
from django.contrib import messages
from .models import YoutubeModel

@admin.action(description='clear users cache')
def clear_users_cache(modeladmin, request, queryset):
    cache.delete('user_list')
    messages.success(request, 'users cache cleared successfully.')

@admin.register(YoutubeModel)
class YoutubeAdmin(admin.ModelAdmin):
    list_display = ['name', 'email', 'subscribers']
    actions = [clear_users_cache]

Deleting the cache is useful when database data changes and you want the next request to fetch fresh data.

Admin changes data
→
Delete user_list
→
Next request gets fresh DB data

12. Common Developer Mistakes
  1. Using different cache keys in get() and set().
  2. Forgetting or misunderstanding the timeout.
  3. Assuming cache is permanent storage.
  4. Ignoring stale data and cache invalidation.
  5. Expecting LocMemCache to be shared automatically across multiple application servers/processes.
  6. Caching everything instead of frequently used or expensive data.
  7. Testing only the cache-hit path and not the cache-miss path.
Production point: LocMemCache is local to the process. For a distributed application, a shared cache such as Redis is commonly used.

On the first request, the application gets the data from the database and stores it in cache for 60 seconds. Later requests can read from cache. I also added a Django Admin action to delete the cache when fresh data is required."
