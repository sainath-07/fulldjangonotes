Django Per-View Cache

Cache the response of one specific Django view for a fixed amount of time.

1. Class Overview
Main idea: Django's @cache_page() decorator can cache the response generated by a particular view for a specified number of seconds.

In this example, the user_list view is cached for 30 seconds.

2. What is Per-View Cache?
Definition

Per-view caching means caching the response of an individual Django view for a specified period.

@cache_page(30)
def user_list(request):
    ...
Simple meaning: Cache one view's result so repeated requests can reuse it for a short time.

4. How Does It Work?
1. Request: User opens /users/.
2. Cache check: Django checks whether a valid cached response exists.
3. Cache hit: Django returns the cached response without executing the view again for that request.
4. Cache miss: Django executes the view.
5. Response: The generated response can be cached for the configured timeout.
6. Expiry: After 30 seconds, a later request can generate a fresh response.

5. When to Use Per-View Cache?
Good use cases
  • Frequently requested views.
  • Views with expensive database queries.
  • Pages whose response does not need to change on every request.
  • Public/read-heavy pages where short-lived stale data is acceptable.
  • Product lists, blog pages, category pages and similar read-heavy pages.
Be careful: Avoid blindly caching personalized or sensitive responses. Consider users, sessions, cookies, authentication and headers before caching.

7. blog/views.py — Main Code
from django.shortcuts import render, redirect
from .models import UserModel
from django.views.decorators.cache import cache_page
from django.core.cache import cache

@cache_page(30)
def user_list(request):
    print('Fetching user list from database')
    users = UserModel.objects.all()
    return render(request, 'blog/user_list.html', {'users': users})


def clear(request):
    cache.delete('userlist')
    cache.clear()
    print('cache cleared')
    return redirect('user_list')
What does @cache_page(30) mean?

30 is the cache timeout in seconds. Django caches the response of this view for that period.

Important: Per-view caching caches the response. It is different from manually caching a queryset with cache.get() and cache.set().
Why print the database message?

It helps you observe whether the view actually runs. On a valid cache hit, the cached response can be returned without running the view body.

Cache MISS

No valid cached response exists.

The generated response can then be cached.

Key point: The decorator handles response caching so you do not have to manually call cache.get() and cache.set() for this basic use case.
11. Clearing the Cache
def clear(request):
    cache.delete('userlist')
    cache.clear()
    print('cache cleared')
    return redirect('user_list')
cache.delete()

Deletes a cache entry for the supplied key if it exists.

cache.clear()

Clears all entries from the configured cache backend.

Important for this example: @cache_page(30) generates the cache key for the view response. Therefore, cache.delete('userlist') does not necessarily target the response generated by @cache_page(30). The following cache.clear() clears the entire configured cache.
Production advice: Avoid broad cache.clear() when unrelated cached data is also stored. Prefer targeted invalidation when appropriate.
12. How to Test
Step 1: Start the Django server.
Step 2: Open /users/.
Step 3: First request: the view runs and database data is loaded.
Step 4: Refresh within 30 seconds.
Step 5: The cached response can be returned without executing the view again.
Step 6: Wait more than 30 seconds and request again; a fresh response can be generated.
Learning trick: Watch the terminal for Fetching user list from database while refreshing.
13. Common Developer Mistakes
  1. Caching personalized responses: Consider authentication, sessions, cookies and user-specific content.
  2. Choosing a timeout without considering freshness: Longer cache life can mean older data.
  3. Thinking cache is permanent: Cache should be rebuildable.
  4. Using cache.clear() unnecessarily: It can remove unrelated cache entries.
  5. Assuming cache.delete('userlist') clears @cache_page(30): The decorator-generated key may be different.
  6. Caching every view: Cache where repeated work is expensive and the response can safely be reused.
