Class 41 — Class Based Views & CRUD Operations

Goal of this class

Build Create, Read, Update and Delete operations using Django's generic class based views.

Big idea: Django provides ready-made generic views such as ListView, DetailView, CreateView, UpdateView and DeleteView. They remove a lot of repeated CRUD code.
Model: Post | +-------------------+ | | v v URLs Templates | v Class Based Views | +--> ListView +--> DetailView +--> CreateView +--> UpdateView +--> DeleteView
1. What Are Class Based Views?

A class based view, or CBV, is a Django view written as a Python class instead of a function.

Django's generic class based views give us reusable classes for common web tasks.

from django.views.generic import ListView

class PostListView(ListView):
    model = Post
    template_name = 'blog/post_list.html'
    context_object_name = 'posts'
Simple meaning: Instead of writing all the request-handling logic ourselves, we configure a Django-provided class with the model, template and other options we need.
Common generic views
ViewMain job
ListViewDisplay a list of objects
DetailViewDisplay one object
CreateViewCreate a new object
UpdateViewEdit an existing object
DeleteViewDelete an existing object
2. Class Based View vs Function Based View
Function Based View
from django.shortcuts import render

def post_list(request):
    posts = Post.objects.all()
    return render(
        request,
        'blog/post_list.html',
        {'posts': posts}
    )
Class Based View
from django.views.generic import ListView

class PostListView(ListView):
    model = Post
    template_name = 'blog/post_list.html'
    context_object_name = 'posts'
Function Based ViewClass Based View
Uses a functionUses a class
Very explicit controlUses reusable Django behavior
Easy to start and understandExcellent for standard patterns
Can become repetitive for CRUDCan greatly reduce repeated CRUD code
Good for unusual/custom flowsGood for common CRUD and reusable behavior
Important: CBVs are not automatically “better” than FBVs. The right choice depends on the problem, readability and how much customization is needed.
3. Which One Should I Use?
Need a Django view | +-----------+-----------+ | | Standard pattern? Very custom flow? | | YES YES | | v v Consider CBV Consider FBV | v Can generic view solve most of it? / \ YES NO | | v v Use generic CBV Custom CBV or FBV
Use a Class Based View when:
  • The task matches a standard Django pattern.
  • You are building CRUD pages.
  • You want to reuse or extend class behavior.
  • You want to use generic views such as ListView or CreateView.
Use a Function Based View when:
  • The request flow is small and very custom.
  • Explicit step-by-step code is easier to understand.
  • The generic CBV would require too much customization.
Best interview answer: “I choose based on the use case, not because one style is always better. For standard CRUD and reusable patterns I prefer generic CBVs. For small or highly custom request flows, an FBV can be clearer.”
What is used most in current technology?

There is no single universal answer. Modern Django projects use both FBVs and CBVs. Generic CBVs are common for standard CRUD because they reduce boilerplate, while FBVs remain common where explicit control and simple custom logic are more readable.

Practical rule: Learn both. Be especially comfortable with generic CBVs because they are an important part of Django's built-in toolkit.

5. blog_app/urls.py
from .views import PostListView, PostDetailView, PostCreateView, PostUpdateView, PostDeleteView
from django.urls import path

urlpatterns = [
    path('', PostListView.as_view(), name="post_list"),
    path('post/<int:pk>/', PostDetailView.as_view(), name="post_detail"),
    path('post/new/', PostCreateView.as_view(), name="post_new"),
    path('post/<int:pk>/edit/', PostUpdateView.as_view(), name="post_edit"),
    path('post/<int:pk>/delete/', PostDeleteView.as_view(), name="post_delete"),
]
Why .as_view()?

A class itself is not directly used as the URL view. Django's as_view() creates the callable view function that Django's URL system can call.

PostListView.as_view()
URL | +--> / --> PostListView.as_view() | +--> /post/5/ --> PostDetailView.as_view() | +--> /post/new/ --> PostCreateView.as_view() | +--> /post/5/edit/ --> PostUpdateView.as_view() | +--> /post/5/delete/ --> PostDeleteView.as_view()
Interview tip: Remember: ClassName.as_view() converts the class based view into the callable that Django's URL dispatcher expects.
6. blog_app/views.py — Complete CRUD Views
6.1 Imports
from django.shortcuts import render
from django.views.generic import ListView, DetailView, CreateView, UpdateView, DeleteView
from django.urls import reverse_lazy
from .models import Post
Small cleanup: In this example, render is imported but not used. It can be removed when the file only contains these generic CBVs.
6.2 ListView — Read many objects
class PostListView(ListView):
    model = Post
    template_name = 'blog/post_list.html'
    context_object_name = 'posts'

ListView gets the Post objects and sends them to the template. The custom context name is posts.

6.3 DetailView — Read one object
class PostDetailView(DetailView):
    model = Post
    template_name = 'blog/post_detail.html'
    context_object_name = 'post'

The URL contains pk. Django uses that primary key to find the requested Post object.

6.4 CreateView — Create a Post
class PostCreateView(CreateView):
    model = Post
    template_name = 'blog/post_form.html'
    fields = ['title', 'content']

Django can create a form from the model fields listed in fields.

6.5 UpdateView — Edit a Post
class PostUpdateView(UpdateView):
    model = Post
    template_name = 'blog/post_form.html'
    fields = ['title', 'content']

The same form template can be used for both creating and updating a Post.

6.6 DeleteView — Delete a Post
class PostDeleteView(DeleteView):
    model = Post
    template_name = 'blog/post_confirm_delete.html'
    success_url = reverse_lazy('post_list')
Key difference: Here success_url explicitly says where to go after deletion: post_list.
7. Why Do Create and Update Go to post_detail?

Your comment says that the create and update views move to the post detail page. This usually happens because the model provides get_absolute_url().

def get_absolute_url(self):
    return reverse('post_detail', args=[str(self.id)])
CreateView | v Create Post | v Does model have get_absolute_url()? | v post_detail for the new object UpdateView | v Update Post | v get_absolute_url() | v post_detail for that object

For generic create/update views, Django can use the model's get_absolute_url() as the success destination when no explicit success_url is supplied.

Important comparison: DeleteView in your example has an explicit success_url, so after deletion it goes to the post list instead.

{% block content %}

<p>{{post.content}}</p>

<a class="btn btn-secondary"
   href="{% url 'post_list' %}">Back to all posts</a>

<a class="btn btn-primary"

<a class="btn btn-danger"

8.4 post_form.html
{% extends 'blog/base.html' %}
{% block content %}

<h2>
  {% if form.instance.pk %}
    Edit post
  {% else %}
    New post
  {% endif %}
</h2>

<form method="post" class="mt-3">
  {% csrf_token %}
  {{form.as_p}}

  <button type="submit" class="btn btn-danger">Save</button>
  <a class="btn btn-secondary"
     href="{% url 'post_list' %}">Cancel</a>
</form>

{% endblock %}
Useful idea: The same post_form.html can serve both CreateView and UpdateView. form.instance.pk helps determine whether the form represents an existing object.
8.5 post_confirm_delete.html
{% extends 'blog/base.html' %}
{% block content %}

<h2>Are you sure you want to delete {{post.title}}?</h2>

<form method="post">
  {% csrf_token %}
  <button class="btn btn-primary" type="submit">
    Yes, delete
  </button>

  <a class="btn btn-secondary"
     href="{% url 'post_detail' post.pk %}">
    Cancel
  </a>
</form>

{% endblock %}
Security rule: Keep {% csrf_token %} inside POST forms that change server-side data.

10. Important Generic View Concepts
model

Tells the generic view which Django model it should work with.

model = Post
template_name

Tells the view which template should render the page.

template_name = 'blog/post_list.html'
context_object_name

Lets you choose the variable name available inside the template.

context_object_name = 'posts'
fields

For CreateView and UpdateView, tells Django which model fields should be included in the generated form.

fields = ['title', 'content']
success_url

Explicitly tells the view where to redirect after a successful operation.

success_url = reverse_lazy('post_list')
Why reverse_lazy()? It lets Django resolve the URL name lazily, which is useful in class attributes that are evaluated when the module is loaded.
11. Common Mistakes
  1. Forgetting .as_view() in urls.py.
  2. Using a template path that does not match the actual template location.
  3. Forgetting fields in CreateView or UpdateView when relying on Django's generated ModelForm.
  4. Forgetting {% csrf_token %} in POST forms.
  5. Expecting DeleteView to automatically return to the list when an explicit success_url has not been configured.
  6. Confusing pk in the URL with a normal template variable.
  7. Writing a huge custom CBV when a simple FBV would be easier to understand.
  8. Assuming CBV always means less code. Complex overrides can make a CBV harder to read.
Developer rule: Less code is not always better code. Prefer the solution that is easiest for another developer to understand and maintain.
12. Interview Questions & Tips
Q1. What is a Class Based View?

A CBV is a Django view implemented as a Python class. Django provides generic CBVs for common tasks such as listing, displaying, creating, updating and deleting objects.

Q2. What is the difference between FBV and CBV?

FBVs use functions and make the request flow explicit. CBVs use classes and can reuse Django's generic behavior through inheritance and configuration.

Q3. Why use ListView?

ListView provides the common behavior needed to retrieve and display a list of model objects without writing all of that logic manually.

Q4. Why use CreateView and UpdateView?

They provide reusable behavior for displaying a model form, validating submitted data and creating or updating the model object.

Q5. What does as_view() do?

It creates the callable view used by Django's URL dispatcher from the class based view.

Q6. What is get_absolute_url() used for?

It provides a canonical URL for a model object. Generic create/update behavior can use it as the success destination when no explicit success URL is supplied.

Q7. Why is DeleteView different in this example?

Because it explicitly sets success_url = reverse_lazy('post_list'), so after deletion Django redirects to the list page.

🎯 Interview tip

When explaining CBVs, don't just name the classes. Explain the problem they solve: “Generic CBVs reduce repeated code for standard Django patterns such as CRUD, while still allowing us to customize behavior when needed.”
