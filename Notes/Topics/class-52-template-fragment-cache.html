1. What is a Template Fragment Cache?

Definition

A fragment is one small part of a template. A template fragment cache saves the finished HTML of that part, so Django does not need to build it again on every request.

We mark the part using the {% cache %} tag, and close it with {% endcache %}.

Layman example

Imagine a tea shop that sells snacks all day. The snack box is filled once in the morning and kept on the counter. Each customer just takes a snack from the box.

But the shopkeeper still greets each customer freshly. The greeting is not saved, but the snack box is. Only one part is saved. That saved part is the fragment cache.

Diagram: one page, many parts

Interview tip: Say it in one line: "Template fragment caching saves the rendered HTML of one part of a template, so Django can skip the work for that part."

2. Why Do We Need It?

Definition

Building a template part can be slow when it has a loop, a database query, or heavy formatting. If the result is the same for many visitors, it is a waste to build it again and again. Fragment caching does this work once and reuses the result.

Layman example

A teacher writes the same homework on the board for every class. Instead of writing it again for each student, the teacher writes it once, and all students read the same board. Less work, same result.

Benefits

  • Faster pages: Django skips the loop and sends the saved HTML.
  • Less database work: On a cache hit, the query for that part does not run at all.
  • Lower server load: The server can handle more visitors with the same power.
  • Partial control: You cache only the slow part, and the rest of the page stays fresh.
  • Easy to add: Only two template tags are needed, and the view stays the same.
Good to know: In our example, the view writes UserModel.objects.all(). Django queries are lazy, which means the database is only read when the template loops over users. When the fragment is cached, the loop is skipped, so the database is never touched.

3. When Should We Use It?

Definition

Use it when one part of a page is slow to build, is shown often, and does not change every second. It is best when only a part of the page should be cached and the rest must stay fresh.

Layman example

A shop puts up a "Top 10 Products" board and updates it once a day. Everyone reads the same board. But the cart is different for each customer, so it is never copied from another customer.

Good time to use it
  • Sidebars, menus, footers and "popular posts" lists.
  • Lists that take a heavy query to build.
  • Parts of a page shared by many visitors.
  • Data that changes slowly, like blog lists or product lists.
  • A page where only one block is slow.
Time to avoid it
  • Live data such as scores, prices or chat messages.
  • Private data (name, cart, account details) cached under a shared name.
  • Small parts that are already very fast.
  • Pages where the user must always see the newest data.

Interview tip: If asked "Why not cache the full page?", answer: "Because some parts, like the logged-in user's name, must stay fresh. Fragment caching lets me cache only the slow, shared part."

4. How Does It Work?

Definition

When Django reaches the {% cache %} tag, it checks the cache for a saved copy of that block.

  • Cache hit: A fresh copy exists. Django uses it and skips the block.
  • Cache miss: No copy, or it has expired. Django runs the block, saves the HTML, and uses it.

Layman example

A photocopy shop keeps a copy of a popular form. If a customer asks for it, the clerk gives the ready copy (hit). If the copy is old or missing, the clerk prints a new one, keeps one aside for the next person, and hands it over (miss). After 20 seconds, the kept copy is thrown away.

Diagram: request flow

Both paths end the same way: the finished page is sent to the browser.

Step by step

  1. The browser opens /users/. Django runs the user_list view.
  2. The view creates users (no database read yet, because queries are lazy) and renders the template.
  3. The template reaches {% cache 20 user_list_cache %}. Django looks for a saved copy named user_list_cache.
  4. Hit: a fresh copy exists, so Django inserts it and skips everything up to {% endcache %}.
  5. Miss: Django runs the loop, reads the users from the database, builds the HTML, and saves it for 20 seconds.
  6. The full page is sent to the browser. After 20 seconds the saved copy expires, and the next visit is a miss again.
Where is the copy saved? In this class, we used the file-based cache. Django saves each cached item as a small file inside the folder template_caching. You can open that folder and see the files (they end with .djcache).
Interview tip: Mention that the view code does not change. All the caching is done in the template, so it is quick to add.

5. Setup: Enable the File-Based Cache

Fragment caching needs a cache backend. In this class we used the file-based cache. It is easy to set up because it saves cache data as files in a folder.

Definition

FileBasedCache is a Django cache backend that stores every cached item as a file on disk. LOCATION is the folder where these files are kept.

Layman example

It is like a drawer with paper slips. Each cached item is one slip of paper in the drawer. LOCATION tells Django which drawer to use.

Steps

  1. Add the CACHES setting in innerproject/settings.py (see the Code section).
  2. Make sure BASE_DIR exists in settings.py. Django adds it by default.
  3. Create the model and run the normal commands shown below.
  4. Add a few users in the admin site and open /users/.
python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
Different from Class 53: The database cache needs the createcachetable command. The file-based cache does not need it. Django creates the folder by itself when the first item is saved, as long as it has permission to write there.

Two names to check before you run the project

  • Template file name: The view renders 'blog/users.html', but the file in the class notes is called user.html. The names must match, or Django shows TemplateDoesNotExist. Rename the file to users.html, or change the name in the view.
  • App name: The folder is blog_app, but the project urls.py has include('blog.urls'). Use your real app folder name, for example include('blog_app.urls').
innerproject/settings.py Cache settings 
CACHES={
    'default':{
        'BACKEND': 'django.core.cache.backends.filebased.FileBasedCache',
        'LOCATION' : BASE_DIR / 'template_caching',
    }
}
  • 'default' is the main cache that Django uses unless you choose another.
  • BACKEND tells Django to save cache data as files.
  • LOCATION is the folder for those files. BASE_DIR / 'template_caching' means a folder named template_caching inside your project folder.

    path('clear/',views.clear_cache,name='clear'),

]
  • /clear/ removes everything from the cache.
  • /users/ shows the user list.
  • The name values are used in the template ({% url 'clear' %}) and in redirect('user_list').
blog_app/views.py Views 
from django.shortcuts import render, redirect
from django.core.cache import cache
from .models import UserModel

# Create your views here.
def clear_cache(request):
    cache.clear()
    print('Cache cleared successfully')
    return redirect('user_list')   # redirect, not render

def user_list(request):
    users=UserModel.objects.all()
    return render(request,'blog/users.html',{'users':users})

In simple words

CodeMeaning
cache.clear()Deletes every saved item in the cache. For the file-based cache, it removes the cache files from the folder.
redirect('user_list')After clearing, sends the browser to the /users/ page. This is better than render, because the address bar shows /users/ and a page refresh will not clear the cache again.
UserModel.objects.all()Prepares a query for all users. It does not read the database yet (lazy query).
render(request, 'blog/users.html', {...})Builds the page from the template and passes users to it.
Notice: There is no cache code in user_list. The view stays simple. The template does all the caching.

from django.db import models

  • sub stores the number of subscribers. The default is 0.

blog_app/templates/blog/user.html Most important file 
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>User List</title>
</head>
<body>
    <h2>User List: tempalte fragment cache</h2>
    <a href="{% url 'clear' %}">Clear Cache</a>

    {% load cache %}
    {% cache 20 user_list_cache %}
    <ul>
        {% for user in users %}
            <li>{{ user.name }} — {{ user.sub }}</li>
        {% empty %}
            <p>No users found.</p>
        {% endfor %}
    </ul>
    {% endcache %}
</body>
</html>

Line by line in simple words

CodeMeaning
{% load cache %}Turns on the cache tags for this template. Without it, {% cache %} gives an error.
{% cache 20 user_list_cache %}Starts the cached block. 20 is the time in seconds. user_list_cache is the name of this fragment.
{% for user in users %}Makes one list item for each user. This is the work we want to skip when the cache is fresh.
{% empty %}Runs only when there are no users.
{% endcache %}Ends the cached block. Only what is between the two cache tags is saved.
{% url 'clear' %}Builds the link to the /clear/ page. It is outside the cache block, so it is always built fresh.
Layman example: The {% cache %} tag is like a photo frame. Whatever is inside the frame is saved as a photo for 20 seconds. Everything outside the frame is drawn fresh each time.

This example has no print lines for hit and miss, so we test it by changing data in the admin site and watching the page.

Diagram: what happens over time

0 s: Miss (build and save) → 1 to 19 s: Hit (saved HTML) → 20 s: Copy expires → Next visit: Miss (build again)
Layman example: A wall clock that shows the time only once every 20 seconds is fast and cheap to run, but it can be a little behind. Caching gives speed in exchange for freshness. Choose the timeout to match how old the data is allowed to be.

8. Cache Tag Cheat Sheet

SyntaxWhat it doesUsed in class?
{% load cache %}Loads the cache tags into the template.Yes
{% cache 20 name %} ... {% endcache %}Caches the block for 20 seconds under the given name.Yes
{% cache 300 name request.user.id %}Keeps a separate copy for each user by adding an extra value to the key.Extra
cache.clear()Removes every saved item (used in the clear_cache view).Yes
make_template_fragment_key('name')Gives the exact key of one fragment, so you can delete only that fragment with cache.delete(key).Extra

Extra: delete only one fragment

from django.core.cache import cache
from django.core.cache.utils import make_template_fragment_key

key = make_template_fragment_key('user_list_cache')
cache.delete(key)

Layman example

Adding request.user.id is like keeping one lunch box for each student, instead of one box for the whole class.

cache.delete(key) removes one lunch box. cache.clear() throws away all lunch boxes.

9. Common Mistakes and Good Habits

Mistake 1: Forgetting {% load cache %}

If you skip it, Django shows the error "Invalid block tag: 'cache'". Put it at the top of the template, before the first cache tag.

Mistake 2: Template name does not match

The name in render() and the real file name must be the same, including the folder. Here it is blog/users.html.

Mistake 3: Expecting instant updates

For 20 seconds, the page shows the saved copy, even if the database changed. Use a short timeout, or clear the cache or delete the key when data changes.

Mistake 4: Caching private data with a shared name

If a block shows one user's private data, every visitor may see it. Add a unique value, like request.user.id, or do not cache that block.

Watch out: Small typos in the template

The heading says "tempalte" instead of "template". Also, a <p> tag inside a <ul> is not valid HTML. Use <li>No users found.</li> instead.

Good habits

  • Give each fragment a clear name such as user_list_cache.
  • Cache only the slow part, not the whole page.
  • Pick a timeout that matches how often the data changes.
  • Test after adding, editing and clearing data.

10. Interview Questions and Answers

How to answer well: Give the definition first, then a small example, then one trade-off. Keep each answer to three or four sentences.

It is a way to cache only one part of a template. We wrap that part in {% cache %} and {% endcache %}, and Django saves the rendered HTML for the given time.

First write {% load cache %}. Then write {% cache timeout fragment_name %}, followed by the content, and end with {% endcache %}. The timeout is in seconds.

It saves the final rendered HTML of that block, not the Python objects or the queryset.

Not if the query is lazy and is only used inside the cached block. Django runs the query when the template loops over it. On a cache hit, the loop is skipped, so the database is not read. But if the view already used the queryset (for example, by calling len() or looping in Python), the query has already run.

Pass an extra value after the fragment name, for example {% cache 300 sidebar request.user.id %}. Django then keeps a separate copy for each different value.

It is the folder path where Django stores the cache files. Django needs permission to write in that folder.

Wait for the timeout to finish, call cache.clear() to remove everything, or use cache.delete(key) with make_template_fragment_key() to remove only one fragment.

Fragment cache saves the HTML of one block in a template. Low-level cache saves any Python data using cache.get and cache.set. Per-view cache saves the whole page response. Choose the smallest one that solves the problem.

11. Quick Summary

Key points to remember
  • Fragment cache saves the HTML of one part of a template.
  • Write {% load cache %} first, then use {% cache 20 name %} and {% endcache %}.
  • The first load is a miss. Loads within 20 seconds are hits.
  • On a hit, the loop and database query are skipped.
  • FileBasedCache keeps cache files in the LOCATION folder.
  • Use cache.clear() to remove all saved copies.
Template recap

{% cache 20 user_list_cache %}
    ... slow or heavy part here ...
{% endcache %}
