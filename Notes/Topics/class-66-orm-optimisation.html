1. What is select_related?

select_related is a Django ORM queryset method used to optimise queries across ForeignKey and OneToOneField relationships (the "forward" side of a relation, or "single-valued" relations). It performs a SQL JOIN and includes the related object's fields in the same query — avoiding extra database hits.

books = Book.objects.select_related('author').all()
Without select_related, accessing book.author.name for each book triggers a separate query per book — the classic "N+1 query problem".
2. What is prefetch_related?

prefetch_related optimises queries across reverse ForeignKey and Many-to-Many relationships (multi-valued relations). Instead of a JOIN, it runs a separate optimised query for the related objects and then joins the results together in Python.

authors = Author.objects.prefetch_related('books').all()
A JOIN doesn't work well for multi-valued relations (it would duplicate rows), so prefetch_related instead does a second query like WHERE author_id IN (...) and stitches results in memory.
3. Difference Between select_related vs prefetch_related
Aspect select_related prefetch_related
Relationship type ForeignKey, OneToOneField (forward) Reverse ForeignKey, ManyToManyField
SQL mechanism Single query with SQL JOIN Multiple queries, joined in Python
Number of queries 1 2 or more (one per prefetched relation)
Best for Single related object per row Multiple related objects per row
4. What is a ForeignKey?

A ForeignKey is a field type in Django models that creates a many-to-one relationship — linking one model to another. It stores the primary key of the related object, effectively representing a database foreign key constraint.

author=models.ForeignKey(Author,related_name='books',on_delete=models.CASCADE)
  • related_name='books' — lets you access an author's books via author.books.all() (reverse relation)
  • on_delete=models.CASCADE — deletes all related Book rows when the referenced Author is deleted
5. Model Relationships
One-to-One Relation

Each record in Model A relates to exactly one record in Model B, and vice versa.

models.OneToOneField(...)

e.g. User ↔ Profile

One-to-Many Relation

One record in Model A relates to many records in Model B (a ForeignKey).

models.ForeignKey(...)

e.g. Author → many Books (this project's example)

Many-to-Many Relation

Many records in Model A relate to many records in Model B, through a join table.

models.ManyToManyField(...)

e.g. Book ↔ many Genres, Genre ↔ many Books

In this project's models, Book.author is a ForeignKey (one-to-many): one Author can have many Book records, but each Book has exactly one Author.

from django.db import models

# Create your models here.
class Author(models.Model):
    name=models.CharField(max_length=100)

    def __str__(self):
        return self.name

class Book(models.Model):
    title=models.CharField(max_length=100)
    author=models.ForeignKey(Author,related_name='books',on_delete=models.CASCADE)

    def  __str__(self):
        return self.title
blog/serializers.py
from rest_framework import serializers
from .models import Book,Author

class BookSerializer(serializers.ModelSerializer):
    class Meta:
        model=Book
        fields=['id','title','author']


class AuthorSerializer(serializers.ModelSerializer):
    books=BookSerializer(many=True,read_only=True)
    class Meta:
        model=Author
        fields=['id','name','books']

blog/views.py
from rest_framework.response import Response
from rest_framework.decorators import api_view
from .models import Author, Book
from .serializers import AuthorSerializer, BookSerializer


# view to get all books without optimisation
@api_view(['GET'])
def all_books(request):
    books = Book.objects.all()
    serializer = BookSerializer(books, many=True)
    return Response(serializer.data)


# using select_related to optimise ForeignKey relationships
@api_view(['GET'])
def select_book(request):
    books = Book.objects.select_related('author').all()
    serializer = BookSerializer(books, many=True)
    return Response(serializer.data)


# using prefetch_related to optimise reverse ForeignKey relationships
@api_view(['GET'])
def prefetch_authors(request):
    authors = Author.objects.prefetch_related('books').all()
    serializer = AuthorSerializer(authors, many=True)
    return Response(serializer.data)
8. Interview Tips
1Explain the N+1 query problem clearly.

Fetching a list and then accessing a related field per item without optimisation triggers one query per item — interviewers love asking you to spot and fix this.

2Remember the simple rule: JOIN vs separate query.

select_related = SQL JOIN, single query, forward FK/O2O relations. prefetch_related = extra query, Python-side join, reverse FK/M2M relations.

3Common trick question:

"Can you use select_related on a Many-to-Many field?" — Answer: No, because a JOIN would duplicate rows for multi-valued relations; use prefetch_related instead.

4Know on_delete options.

Be ready to explain CASCADE, PROTECT, SET_NULL, and SET_DEFAULT as behaviors when a referenced ForeignKey object is deleted.

5Be ready to describe related_name.

related_name='books' lets you query in reverse — author.books.all() — instead of the default author.book_set.all().
