1. What is a File-Based Cache?

Definition

A cache is a place where we keep a ready-made copy of some data, so we can get it quickly next time.

A file-based cache keeps this copy in a file on your disk. Django creates a folder (here, my_cache) and saves each cached item as a separate file inside it. These files work as the cache.

Layman example

Think of a drawer with paper slips. Each time you find an answer to a hard question, you write it on a slip and put it in the drawer. Next time someone asks the same question, you open the drawer and read the slip instead of searching the big library again.

The drawer is the folder. Each slip is one cache file.

Diagram: what the folder looks like

The file names above are short examples. Real names are long, random-looking text that Django creates from the cache key.

Interview tip: Say it in one line: "A file-based cache stores each cached item as a file on disk, in the folder given by LOCATION."

2. Use Cases: When Should We Use It?

Definition

Use a file-based cache when you want caching that is simple to set up, needs no extra software, and should stay after the server restarts. It is a good middle step between "no cache" and a full cache server like Redis.

Layman example

A small shop does not need a big warehouse. A shelf behind the counter is enough to keep popular items close. It is cheap, easy to set up, and the items stay on the shelf even after the shop closes for the night.

Good time to use it
  • Small or medium websites on a single server.
  • Learning and testing caching on your own computer.
  • When you cannot install Redis or Memcached.
  • Heavy database queries, reports or lists that are read often.
  • Data that changes rarely, such as a user list or product list.
  • When the cache should survive a server restart.
Time to avoid it
  • Many servers that must share one cache (each server has its own folder).
  • Very high traffic where top speed is needed.
  • Servers where the disk is temporary and files are lost (some container or serverless setups).
  • Live data that must always be fresh.
  • Private data cached under one shared key.

Which cache type should I pick?

Interview tip: Always mention the trade-off. File-based cache is easy and lasting, but it is slower than memory-based caches because it reads from the disk.

3. How Does It Work?

Definition

The view first asks the cache for a saved copy, using a key (here, user_list).

  • Cache hit: A cache file exists and is not expired. Django reads it and returns the data.
  • Cache miss: No file, or the file has expired. Django reads the database, then writes a new cache file.

Layman example

You ask a clerk for a form. The clerk checks the drawer. If a fresh copy is there, the clerk hands it over at once (hit). If not, the clerk goes to the big record room, makes a copy, puts one in the drawer for the next person, and hands you the form (miss). Copies older than 5 minutes are thrown away.

Diagram: request flow

Both paths end the same way: the view sends the data to the template, and the browser shows the page.

Step by step

  1. The browser opens /users/. Django runs the user_profile_list view.
  2. The view calls cache.get('user_list'). Django looks for the matching file in the my_cache folder.
  3. Hit: the file is found and not expired, so Django reads the data from it. The view prints feching data from cache.
  4. Miss: the file is missing or expired. The view prints cache not hit and reads all users from the database.
  5. On a miss, the view calls cache.set('user_list', user_data, timeout=300). Django writes a new cache file that stays valid for 300 seconds (5 minutes).
  6. The view sends the users to the template, and the page is shown.
Good to know: A Django query is lazy, but saving it in the cache forces it to load all its rows first. So on a miss, the database is read when cache.set runs. On a hit, the saved rows come straight from the file.
Interview tip: Use the words "hit", "miss", "key" and "timeout" in your answer. It shows that you know the flow, not just the code.

4. Why Do We Need It?

Definition

Reading from the database again and again for the same data wastes time and power. A file-based cache does the hard work once, saves the result in a file, and reuses it until the timeout ends.

Layman example

A teacher writes the day's homework on a notice board once, instead of telling each student one by one. Everyone reads the same board. Less work for the teacher, and the answer is quick for everyone.

Benefits

  • Faster pages: Reading a saved file is usually quicker than running a heavy query.
  • Less database load: The database is asked less often.
  • No extra software: No Redis or Memcached server is needed.
  • Lasts after restart: The files stay on the disk when the server stops and starts again.
  • Easy to set up: Only a small CACHES setting is needed. There is no extra command to run.
  • Easy to check: You can open the folder and see the cache files yourself.
Interview tip: A strong answer has two sides. "It is simple and it lasts, but it is slower than memory caches and does not share between servers."

5. Settings Explained

All the setup for the file-based cache is inside the CACHES setting. You do not need to run a create-table command like in the database cache. Django makes the folder for you when the first item is saved, as long as it has permission to write there.

CACHES={
    'default':{
        'BACKEND': 'django.core.cache.backends.filebased.FileBasedCache',
        'LOCATION' : BASE_DIR / 'my_cache',
        'TIMEOUT' :300,
        'OPTIONS': {
            'MAX_ENTRIES':1000
        }
    }
}
SettingWhat it meansLayman example
'default' The name of the main cache. When we write from django.core.cache import cache, Django uses this one. The main drawer of the office.
BACKEND Tells Django to save cache data as files. Choosing to keep answers on paper slips.
LOCATION The folder where cache files are stored. BASE_DIR / 'my_cache' means a folder named my_cache inside your project folder. The address of the drawer.
TIMEOUT How long an item stays valid, in seconds. 300 seconds is 5 minutes. None means it never expires. 0 means do not cache. The "use before" date on a milk packet.
OPTIONS → MAX_ENTRIES The most items the cache may hold. When it is full, Django removes some old entries to make space. If you do not set it, the default is 300. The drawer holds only 1000 slips. When it is full, some old slips are thrown out.
Extra option: CULL_FREQUENCY (inside OPTIONS) decides how many entries are removed when the cache is full. The default is 3, which means about one third. A value of 0 clears the whole cache at that moment.
Folder permission: The user running Django must be able to read and write in the my_cache folder. If not, Django will show a "permission denied" error.

blog_app/views.py Most important file 
from django.shortcuts import render
from .models import UserProfile
from django.core.cache  import cache

# Create your views here.
def user_profile_list(request):
    user_data=cache.get('user_list')

    if not user_data:
        print('cache not hit:  ')
        user_data = UserProfile.objects.all()
        cache.set('user_list',user_data,timeout=300)

    else:
        print('feching data from cache')

    return render(request,'user_profile_list.html',{'users':user_data})

Line by line in simple words

CodeMeaning
from django.core.cache import cacheBrings in the tool we use to read and write the cache.
cache.get('user_list')Looks for the saved data with the key user_list. If the file is missing or expired, it gives None.

UserProfile.objects.all()Reads all users from the main database table.
cache.set('user_list', user_data, timeout=300)Writes the users to a cache file that stays valid for 300 seconds. This value is the same as the default TIMEOUT, so here it repeats the setting. Use it when one item needs a different time.

render(..., {'users': user_data})Builds the page from the template and passes the users to it.
Layman example: cache.get means "check the drawer for a slip". cache.set means "write a new slip and put it in the drawer for 5 minutes".

7. See It Working: Demo Walkthrough

First, run makemigrations, migrate, createsuperuser and runserver. Add a few users in the admin site. Then watch the terminal, where the print() lines tell you if the cache was used. You can also open the my_cache folder to see the files.

#What you doTerminal showsWhat it means
1Open /users/ for the first timecache not hitNo file yet, so Django read the database and wrote a cache file in my_cache.
2Refresh the pagefeching data from cacheThe data came from the cache file.
3Add a new user in admin, then refresh /users/feching data from cacheThe new user is not shown. The page still uses the saved file.
4Stop the server, start it again, and refreshfeching data from cacheThe file is still on the disk, so the cache survived the restart.
5Wait 5 minutes, or delete the files in my_cache, and refreshcache not hitThe old copy is gone, so Django read fresh data. The new user now appears.

Diagram: what happens over time

0 s: Miss (write file) → 1 to 299 s: Hit (read file) → 300 s: File expires → Next request: Miss (write new file)
How to clear the cache by hand: This project has no clear button. You can open the Django shell with python manage.py shell and run the two lines below. Or just delete the files inside the my_cache folder. 
from django.core.cache import cache
cache.clear()
Layman example: A newspaper printed at 8 AM will not show news from 9 AM. You must wait for the next print. In the same way, cached data can be a little old until it expires. This is the main trade-off of caching: speed in exchange for freshness.

File-based cache at a glance

Strong points
  • Simple setup, no extra server.
  • Data stays after restart.
  • Works with many processes on the same machine.
  • Easy to inspect and clear.
Weak points
  • Slower than memory-based caches.
  • Not shared between different servers.
  • Uses disk space (limit it with MAX_ENTRIES).
  • Needs a folder that Django can write to.

9. Common Mistakes and Good Habits

Mistake 1: Expecting instant updates

When data changes, the page still shows the old copy until the timeout ends. Use a shorter timeout, or delete the key or clear the cache when data changes.

Mistake 2: Folder without permission

If Django cannot write to the LOCATION folder, it will show a permission error. Make sure the user that runs Django can read and write there.

Mistake 3: Using it across many servers

Each server has its own my_cache folder. So one server may show old data while another shows new data. For many servers, use a shared cache such as Redis or Memcached.

Mistake 4: Caching private data under a shared key

If the data is different for each user, add the user's id to the key, for example 'user_list_' + str(request.user.id). Otherwise, one user may see another user's data.

Watch out: An empty list looks like a miss

The line if not user_data: is also true when the list is empty. So if there are no users, every request will be a miss. A more exact check is if user_data is None:.

Watch out: Small typos in the notes

  • The print text says "feching". The correct spelling is "fetching".
  • The notes call the files setting.py and blog_app.py/urls.py. The real names are settings.py and blog_app/urls.py.
  • A <p> tag inside <tbody> is not valid HTML. Use <tr><td colspan="4">No users found...</td></tr> instead.

Good habits

  • Add the my_cache folder to .gitignore, so cache files do not go into Git.
  • Keep the cache folder private. Do not place it inside a folder that the website shows to the public.
  • Choose a timeout that matches how often the data changes.
  • Test both a hit and a miss, using print lines or logs.

10. Interview Questions and Answers

How to answer well: Give the definition first, then a small example, then one trade-off. Keep each answer to three or four sentences.

It is a cache backend that saves each cached item as a file in a folder on the disk. Django reads these files to avoid repeating slow queries or heavy work.

In settings.py, set BACKEND to django.core.cache.backends.filebased.FileBasedCache and set LOCATION to a folder path. No extra command is needed.

It is the folder where Django stores the cache files. Django needs permission to read and write in that folder.

TIMEOUT is the default life of a cached item, in seconds. The default value is 300. None means the item never expires, and 0 means the item is not cached.

It is the maximum number of items the cache can hold. When the limit is reached, Django removes some old entries to make space. The default is 300. It also stops the cache folder from growing without limit.

The setting is the default for all items. The value in cache.set() is for that one item and overrides the default. Here both are 300, so we could leave it out, but it is useful when one item needs a different time.

File-based cache saves data in files and database cache saves it in a table. Both survive a restart and need no extra server, but both are slower than memory. Memory caches (local memory, Redis, Memcached) are faster, but local memory is lost on restart, and Redis and Memcached need a separate server.

It is slower than memory caches, it is not shared between different servers, it uses disk space, and it does not suit setups where the disk is temporary. It works best on a single server.

Wait for the timeout, call cache.clear() to remove everything, call cache.delete(key) to remove one item, or delete the files in the cache folder.

11. Quick Summary

Key points to remember
  • File-based cache saves each cached item as a file in a folder.
  • LOCATION is the folder (BASE_DIR / 'my_cache').
  • TIMEOUT is the life of an item in seconds. The default is 300.
  • MAX_ENTRIES limits how many items are kept.
  • No extra command is needed to start using it.
  • get to read, set to save. First load is a miss, later loads are hits.
  • Best for a single server. It is simple and lasting, but slower than memory caches.
Pattern recap
data = cache.get('key')

if not data:
    data = Model.objects.all()
    cache.set('key', data, timeout=300)
