1. What is Middleware?

Middleware is a layer between the request and the response.

Django middleware is code that runs during Django's request and response process. It can inspect a request before the view runs and inspect or change the response after the view has finished.

Easy definition: Middleware is like a checkpoint between the browser and your Django view. It lets you apply common logic without putting the same code inside every view.
Browser | | HTTP Request v Middleware | v View | | HttpResponse v Middleware | v Browser
2. How Middleware Works

A request normally travels through the middleware stack before reaching the view. The response then travels back through the middleware layers.

Client | v Middleware 1 | v Middleware 2 | v Middleware 3 | v View | v Response | ^ Middleware 3 | ^ Middleware 2 | ^ Middleware 1 | ^ Client
  1. Client sends a request.
  2. Django passes it through the middleware stack.
  3. Middleware can inspect, modify or reject the request.
  4. The request reaches the view if processing continues.
  5. The view creates a response.
  6. The response travels back through middleware.
  7. The client receives the final response.
Remember: Middleware can work on both sides of the view: during request processing and during response processing.
3. Where Do We Use Middleware?

Middleware is useful for common logic that applies to many requests.

Authentication check

Check whether a user is authenticated before allowing a request to continue.

Request and response logging

Record URLs, timestamps, status codes and other useful information.

IP blocking

Reject requests from blocked IP addresses when appropriate.

Language or session management

Read request, cookie or session information and prepare common data.

Performance timing

Measure how long requests take and identify slow requests.

Security processing

Apply common request or response security checks centrally.

Rule of thumb: If the same request/response logic is repeated across many views, consider middleware.
4. What Middleware Allows Us To Do
Authentication

Check user state before the request reaches the view.

5. Custom Middleware Example
Request and response logging
import datetime
from django.http import HttpResponse
from django.utils.deprecation import MiddlewareMixin

class SimpleLogMiddleware(MiddlewareMixin):

    def process_request(self, request):
        print(f'[{datetime.datetime.now()}] Request Url:{request.path}')

    def process_response(self, request, response):
        print(f'[{datetime.datetime.now()}] Response status code:{response.status_code}')
        return response
What happens? process_request() handles request-side work. process_response() handles response-side work. Returning the response passes it onward.
Block an IP
class BlockIPMiddleware(MiddlewareMixin):
    BLOCKED_IPS = ['127.0.0.1']

    def process_request(self, request):
        ip = request.META.get('REMOTE_ADDR')

        if ip in self.BLOCKED_IPS:
            return HttpResponse('Your IP is blocked.')
Incoming request | v Read REMOTE_ADDR | v Is IP blocked? / \ YES NO | | v v Response Continue to view
Important: Returning an HttpResponse during request processing can stop the request from continuing to the view. If the IP is not blocked, the middleware lets normal processing continue.
Production note: A hard-coded IP list is useful for learning, but production security may use configuration, a database, reverse proxy, WAF or rate limiting depending on the requirement.
6. Add Middleware to settings.py

Django loads middleware from the MIDDLEWARE list in settings.py.

innerproject/settings.py

MIDDLEWARE = [
    'django.middleware.security.SecurityMiddleware',
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.middleware.common.CommonMiddleware',
    'django.middleware.csrf.CsrfViewMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.messages.middleware.MessageMiddleware',
    'django.middleware.clickjacking.XFrameOptionsMiddleware',
    'blog.middleware.SimpleLogMiddleware',
    'blog.middleware.BlockIPMiddleware',
]
How to read this path
'blog.middleware.SimpleLogMiddleware'
'blog.middleware.SimpleLogMiddleware' | +--> blog = Django app | +--> middleware = Python module | +--> SimpleLogMiddleware = class

The normal pattern is app_name.module_name.ClassName.

Order matters: Middleware runs as a stack, so changing the order can change application behavior. Some middleware depends on work performed by earlier middleware.

9. Performance Timing Example
import time
from django.utils.deprecation import MiddlewareMixin

class TimingMiddleware(MiddlewareMixin):

    def process_request(self, request):
        request.start_time = time.perf_counter()

    def process_response(self, request, response):
        elapsed = time.perf_counter() - request.start_time
        print(f"{request.path} took {elapsed:.4f} seconds")
        return response
Request | v Record start time | v View executes | v Response created | v Calculate elapsed time | v Log timing
Benefit: Timing logic can be centralized instead of being copied into every view.
10. Interview Questions & Tips
Q1. What is middleware?

Middleware is a processing layer in Django's request/response pipeline. It can inspect, modify or reject requests and can inspect or modify responses.

Q2. Why use middleware?

To handle common cross-cutting logic centrally, such as logging, authentication-related checks, security, sessions and performance monitoring.

Q3. Can middleware stop a request?

Yes. Request processing can return a response before the request reaches the view.

Q4. Why does middleware order matter?

Middleware can depend on information or behavior established by another middleware, so order can affect the result.

Q5. Why return the response?

Response middleware normally needs to pass the response onward unless it intentionally replaces it.

🎯 Interview-ready answer

“Middleware is a layer in Django's request/response pipeline. It is used for cross-cutting concerns such as logging, authentication checks, security, session handling and performance monitoring, so we do not repeat the same logic in every view.”
