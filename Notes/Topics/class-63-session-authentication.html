1. What is Session Authentication?

Session Authentication uses Django's built-in session framework to authenticate requests. When a user logs in (e.g. through the browsable API login page or Django's admin), Django creates a session on the server and sends the client a sessionid cookie.

On every subsequent request, the browser automatically sends this cookie back. DRF's rest_framework.authentication.SessionAuthentication reads the session ID, looks up the session on the server, and identifies the logged-in user — attaching it to request.user.

Session Authentication is tightly coupled with Django's session middleware and is mainly designed for browser-based clients that share cookies with the API (e.g. the DRF browsable API, or a web app on the same domain).
2. How It Works Behind Login Sessions (Cookies)
  1. Login: User submits credentials (username/password) to a login view.
  2. Session Created: Django creates a session record on the server (in DB/cache) and generates a unique session key.
  3. Cookie Set: The server responds with a Set-Cookie: sessionid=<key> header. The browser stores this cookie.
  4. Subsequent Requests: The browser automatically attaches the sessionid cookie to every request to that domain.
  5. Server Lookup: SessionAuthentication reads the cookie, fetches the matching session, and resolves the logged-in User object.
  6. CSRF Protection: Since cookies are sent automatically by the browser, unsafe methods (POST, PUT, DELETE) require a valid CSRF token to prevent Cross-Site Request Forgery.
Because cookies are sent automatically by browsers, Session Authentication needs CSRF protection for unsafe HTTP methods — this is different from token-based schemes where CSRF isn't a concern.
3. What is IsAuthenticatedOrReadOnly?

IsAuthenticatedOrReadOnly is a DRF permission class that:

Request TypeWho can access?
Safe / read-only methods — GET, HEAD, OPTIONS Anyone — authenticated or anonymous
Unsafe / write methods — POST, PUT, PATCH, DELETE Only authenticated users
It's a hybrid of AllowAny (for reads) and IsAuthenticated (for writes) — perfect for public-read, authenticated-write APIs like blogs.
4. Key Questions Answered
Does IsAuthenticatedOrReadOnly provide access to use the GET method without any authentication?
Yes. GET (along with HEAD and OPTIONS) is treated as a "safe" method, so IsAuthenticatedOrReadOnly allows any user — authenticated or not — to perform GET requests freely. Only write operations (POST, PUT, PATCH, DELETE) require the user to be logged in.
5. When to Use Session Authentication
  • Web applications where the frontend and API share the same domain/session (server-rendered or same-origin SPA)
  • When using Django's browsable API or Django Admin alongside DRF
  • Applications that already rely on Django's login system and session middleware
  • Avoid for mobile apps or cross-domain/third-party clients — prefer Token or JWT Authentication there, since cookies don't transfer well across native clients/domains

from rest_framework.decorators  import api_view
from rest_framework.response import Response
from .models import BlogModel
from .serializers  import Blogserializers
from  rest_framework import status

@api_view(['GET','POST'])
def blog_list(request):
    if request.method == 'GET':
        blog = BlogModel.objects.all()
        serailzer = Blogserializers(blog, many=True)   # GET: serialize queryset with many=True, no data=
        return Response(serailzer.data)

    if request.method == 'POST':
        serailzer = Blogserializers(data=request.data)
        if serailzer.is_valid():
            serailzer.save()
            return Response(serailzer.data, status=status.HTTP_201_CREATED)   # 201 for created
        return Response(serailzer.errors, status=status.HTTP_400_BAD_REQUEST)  # 400 for invalid data

8. Interview Tips
1Explain the cookie lifecycle clearly.

Login → server creates session → sessionid cookie sent → browser auto-attaches it on future requests → server resolves the user from the session store.

2Know why CSRF matters here.

Because the browser sends cookies automatically (even for requests it didn't intend), Session Authentication needs CSRF tokens on unsafe methods to prevent forged requests from other sites.

3Compare with Token/JWT Authentication.

Session auth is stateful (server stores session data) and cookie-based; Token/JWT auth is typically stateless and header-based — better suited for mobile apps and cross-domain APIs.

4Common trick question:

"Can an anonymous user fetch data from an endpoint using IsAuthenticatedOrReadOnly?" — Answer confidently: Yes, for safe methods like GET; write methods still need authentication.

5Be ready to explain scalability trade-offs.

Session Authentication requires server-side session storage, which can complicate horizontal scaling compared to stateless token-based schemes.
